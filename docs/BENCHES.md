# The benches: the hot path's p50 and p99 (#71)

Four criterion benches of the wallet's hot path, on a file-backed SQLite wallet of 1,000 and 10,000 coins (seven in ten mined, two own change unmined, one received unmined) and the toolbox's mock services; nothing reaches the network.

| bench | what one call is |
|---|---|
| `gate_assess` | the spend gate's assessment, for a need and for all |
| `create_action_signed` | the lock, the spend guard, the gate's door, a signed noSend action, aborted after the clock |
| `internalize_action` | one BRC-29 payment with its proof, and the post word |
| `list_outputs` | a list of 100 |

Each call is timed on its own; p50 and p99 are over the calls of criterion's measurement samples (its warm-up calls are dropped), one JSON per bench id. `create_action_signed` and `internalize_action` change the wallet, so each of their calls runs on its own copy of the built database, made before the clock starts: the wallet holds exactly 1,000 (or 10,000) coins and nothing an earlier call left when every call starts, and the benches assert the coin count before each call and after each batch.

**The sample floor.** Every bench id takes 100 samples in criterion's flat mode, which gives each sample the same call count and at least one, so a p99 rests on at least 100 calls (the 99th of 100 at the least); `tools/bench-compare` fails a result of fewer. The measure times buy more than the floor where the call is quick: on the lane's machine `gate_assess` is about 3 ms (need) and 20 ms (all) a call at 1,000 coins and 80 ms and 260 ms at 10,000, so 100 calls of `all` at 10,000 need 26 s and the 90 s it is given is about 340; `create_action_signed` is about 8 ms and 130 ms (100 calls need 13 s; 30 s is about 230); `internalize_action` and `list_outputs` are a few milliseconds and run thousands. A measure time too short for 100 calls on a slower machine is stretched by criterion, which says so.

```bash
tools/bench-compare                    # a developer's reading against this machine's entry; exit 0
tools/bench-compare --record           # write this machine's developer entry; refuses a dirty tree
tools/bench-compare --compare-only D   # a reading of the JSON already in D, run nothing
tools/bench-compare --ci [--base B] --out F   # the CI job (below)
python3 tools/test_bench_compare.py    # the gate's planted cases
```

## The gate is the CI runner's, never a developer machine's

On 2026-10-23 four lanes tried to record a baseline on the development Mac (Apple M1 Max, 10 cores, under the other lanes' load) and found p99 swinging by hundreds of percent between back-to-back runs of one tree: `gate_assess/need/1000` +1189.7 percent, `create_action_signed/signed/1000` +104.9 percent and +529.8 percent, `internalize_action/brc29/10000` +393.7 percent, `create_action_signed/signed/10000` -82.3 percent (`/Volumes/Lanes/out/bsv-wallet-cli/oracle-benches-baseline-4/compare.log` and `compare2.log`). A p99 is a tail, and a shared machine's tail is its neighbours'. The gate's baseline is the Linux CI runner's.

**The constants are the tool's.** The gate's profile (`ubuntu-latest`), the margin's default (5 percent), the sample floor (100 calls) and the history floor (five runs) are constants in `tools/bench-compare`; the workflow names none of them. `--ci` is the gate's profile, and a `BENCH_PROFILE` that is not it is refused there. Outside `--ci`, `BENCH_PROFILE` set to anything but the gate's profile is a developer reading.

**Profiles.** Every entry of `benches/baseline.json` is keyed under `profiles` by its profile and the CPU's model and core count: `ubuntu-latest-<cpu>` is a gate entry (`"gate": true`), one per CPU a hosted runner turns out to have, since a runner on another CPU is another machine; `dev-<cpu>` (for example `dev-apple-m1-max-10-cores`) is a developer's reading, which `tools/bench-compare` prints against and exits 0 whatever the numbers, and which CI never reads. Any other key fails the job.

**The gap: the gate is only as strong as the set of CPUs whose entries carry five runs.** The key stays profile and CPU, since hosted runners vary their CPU and a hard failure on a CPU with no entry would fail PRs on the runner's allotment, not on their code. A run that lands on a CPU with no entry gates nothing: the job passes, says so in a `::warning::` annotation naming the CPU and in the job's step summary, and its artifact holds the candidate opening entry for the captain to commit. A run on a CPU whose entry carries fewer than five runs warns and passes. Until every CPU the runners hand out has five runs, some PRs are not gated, and the annotation is where that shows. The nightly on beta is the run meant to fill the entries; as of this commit `nightly.yml` runs no bench, so until it does they fill only as the captain commits a run's artifact.

**An entry** is `profile`, `gate`, `machine` (CPU model and cores), `toolchain` (`rustc -V`), and `runs`: each run its `commit`, `recorded` date, the job's `run_id`, and `benches` (each id's `p50_us`, `p99_us` and `calls`). The margin is the file's (`margin` at the top), one for every entry; an entry carrying its own fails. The reference p99 of a bench is the highest of the entry's runs. The CI job pins the toolchain (1.98.1, the ratchet job's) twice: `RUSTUP_TOOLCHAIN` in the job's env, over any `rust-toolchain.toml` a PR adds, and `tools/bench-compare --ci` refusing a `rustc -V` that is not its constant `TOOLCHAIN_PIN`, so a PR cannot move the run off the entry's toolchain and turn it into a warning. An entry recorded on another compiler is not gated, and the candidate is a re-record on the pin; the pin moves in the tool, both jobs and the entry together.

## Where a gate entry comes from

A gate entry is the CI job's measure and nothing else's. The job checks out the PR's head (`github.event.pull_request.head.sha`, not the merge ref; on a push, the pushed commit), refuses to run unless `BENCH_COMMIT` is that checked-out commit, measures into a directory it made and cleared (`--compare-only` is refused under `--ci`), and stamps each run it writes with that sha. `--record` writes developer entries only.

Nothing stops a person writing a gate entry by hand: the file is text. What stops one landing is the job's check of the tree's file against the base's, below: a new run in the tree must match what the job just measured. The check is the guard, not where the file was written.

## The CI job

1. **The planted cases** (`tools/test_bench_compare.py`) run before the benches: each way a PR could turn the gate off, and the cases the gate lets through.
2. **The tree's baseline is checked against the base's**, read as the ratchet job reads its record (`git show origin/<base>:benches/baseline.json` on a PR, the commit before on a push; a base without the file is a baseline with no entry). Each of these fails the job, whatever the numbers: a changed margin; a gate entry of the base dropped; an entry's machine, toolchain or bench ids changed; a run of the base rewritten or removed; more than one run appended; an appended run, or a opening entry (one run, where the base has none), whose bench ids are not this run's or whose p50 or p99 is not within the margin of this run's measure (the job names each gap); a changed entry for a CPU other than this runner's (the job cannot check it; it is re-run until it lands on that CPU). A opening entry with this run's toolchain where the base's names the old pin is the re-record after a pin move, checked the same way. And an appended run whose p99 is more than the margin over the base's reference fails, in the warn-only period too: this run's measure may be over and only warn, the run the PR commits may never be. Without it a PR in the warn-only period could commit a run 3x slower as the fifth and switch the gate on with it in the reference, and with the gate on a run measured at +4.9 percent could commit +10 percent, the reference creeping a margin per PR. The re-record is the one exception: its p99 over the base's reference (recorded on the old pin) is a `::warning::` annotation and a step-summary line naming the old and the new toolchain and each bench's slowdown, never an error, since a compiler more than the margin slower could otherwise never be re-recorded and the pin never move.
3. **The comparison.** The reference is the base's entry for this runner's CPU, never the tree's: the tree's is checked (step 2) and never compared against. A run the PR appended matches this PR's own measure, so a reference that took it in would let a PR append a slow run and pass with the gate on; the run counts once it is in the base. With no base (a push whose commit before is not fetchable) nothing is gated and the job says so in a warning. Each p99 more than the margin above the reference fails, and a bench of the entry not measured fails. A bench measured and not in the entry is named and not gated (the bench ids of an entry change only with a re-record). A result of fewer than 100 calls fails.
4. **Warn-only until five runs.** Until the base's entry for this runner's CPU carries five runs, a p99 over the margin is a warning and the job exits 0. The Mac's evidence above says one run's p99 says little about the next; whether a hosted runner holds 5 percent is unproven, and five runs of history show its spread before the gate fails anyone's PR. With five, the job gates.
5. **The artifact `bench-baseline`** holds the per-bench JSON and the candidate baseline: the base's file with this run appended to its CPU's entry (the tree's file only when there is no base), or a fresh entry when there is none or the toolchain moved.

**The captain commits a candidate** from a run's artifact (its `baseline.json` as `benches/baseline.json`), in a PR that says so, one run per PR: the CPU's opening entry, then each run of its history. The PR's own job checks the committed run against its own measure; a run whose numbers moved more than the margin between the two fails, and the captain commits the newer run's artifact instead. A lowering after the hot path got faster is not a PR's to make: the reference falls only with a re-record.

**A PR that changes a bench** (its fixtures, its call, its sizes, its ids) records the reason in its commit message: the numbers before it are of another bench. Its new ids are not gated until the entry is re-recorded; a removed or renamed id fails the job by design and lands only on the captain's word with the re-recorded entry.
