## The reference, as read

**Four permission kinds, four admin baskets.** A grant is an on-chain PushDrop token in one of four baskets: `admin protocol-permission` (DPACP: protocol, security level, counterparty, privileged), `admin basket-access` (DBAP: basket), `admin certificate-access` (DCAP: verifier, type, fields, privileged), `admin spending-authorization` (DSAP: `authorizedAmount`, the month's ceiling) ([WPM:418-423](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L418-L423), the token's fields [WPM:356-411](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L356-L411)). Labels ride the protocol kind as `[1, "action label <label>"]` ([WPM:1817-1837](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L1817-L1837)). There is no origin-level "connect" grant: a door the manager does not gate answers any originator.

**The expiry.** Unix seconds; `0` never expires (`expiry > 0 && expiry < now`, [WPM:2900-2903](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L2900-L2903)); spending tokens are indefinite, their ceiling reset by the calendar month in UTC ([WPM:382](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L382), the month's tally [WPM:3296-3334](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L3296-L3334), read from the actions labelled `admin originator <o>` and `admin month <YYYY-MM>`, [WPM:4334](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L4334)). `grantPermission` takes `expiry` (default `0`), `ephemeral` (a one-time grant, no token) and `amount` ([WPM:1160-1181](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L1160-L1181)).

**The originator.** `prepareOriginator` refuses an empty originator, a scheme, credentials, a path, a query, a fragment and an IP address, and returns the normalized hostname with the lookup values (the name as given, the hostname, then any token whose decoded originator normalizes to it) ([WPM:5750-5795](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L5750-L5795)); `normalizeOriginator` lowercases and drops the port: every port of a host shares one grant ([WPM:5702-5729](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L5702-L5729)). The token keeps the raw name beside it (`rawOriginator`, [WPM:375-380](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L375-L380)). ## (1) The store

**The reference's answer.** Four kinds of on-chain token in four admin baskets, each per instance (a protocol and counterparty, a basket, a certificate type), keyed by the normalized hostname, with the raw name kept; an expiry in seconds, `0` never; spending's ceiling per calendar month, its tally read from labelled actions (above).

**The port's choice `[D]`.** Three CLI-owned tables in the wallet's SQLite beside the toolbox's, in a new module `origin_grants` of the library (one module, the only writer of these tables), created as PR 405's `tracker_adopt_checks` is (`ensure_adopt_checks`, `src/store.rs:279-290`, called from the tracker's `ensure_tables`, which reads before it writes, `src/tracker_host.rs:804-815`): the `ensure` reads `sqlite_master` for the three tables and the three indexes by type and name, and when any one is missing runs the whole block below (`IF NOT EXISTS` throughout) in one transaction on the store's writer, so a store that has all six sends nothing to the writer and a store interrupted between a table and its index gains the index at the next start. `has_column` (`src/store.rs:23`) reads a table's columns and cannot see a missing index, so it is not the check here. The toolbox's tables are never touched: no `ALTER`, no index, no trigger on them, no foreign key into them.

```sql
CREATE TABLE IF NOT EXISTS origin_grants (
  grant_id       INTEGER PRIMARY KEY,
  originator     TEXT NOT NULL,          -- the key: the hostname, lowercased, no port, no scheme (WPM normalizeOriginator)
  raw_originator TEXT NOT NULL,          -- as named: the env entry, or the pending row's originator with its port
  scope          TEXT NOT NULL CHECK (scope IN ('wallet', 'spending')),
  amount         INTEGER,                -- spending only: the month's ceiling in satoshis; NULL is no ceiling (env rows only)
  granted_at     INTEGER NOT NULL,       -- unix seconds
  expiry         INTEGER NOT NULL DEFAULT 0, -- unix seconds; 0 never expires
  revoked_at     INTEGER,                -- unix seconds; NULL is live
  source         TEXT NOT NULL CHECK (source IN ('owner', 'env'))
);
CREATE UNIQUE INDEX IF NOT EXISTS origin_grants_key ON origin_grants (originator, scope);

CREATE TABLE IF NOT EXISTS origin_pending (
  pending_id     INTEGER PRIMARY KEY,
  originator     TEXT NOT NULL,          -- the key, as above
  raw_originator TEXT NOT NULL,          -- the Origin's originator with its port (the reference's displayOriginator)
  scope          TEXT NOT NULL CHECK (scope IN ('wallet', 'spending')),
  call           TEXT NOT NULL,          -- the door's path of the call that wrote the row (/listOutputs)
  amount         INTEGER,                -- spending only: the call's satoshis
  renewal        INTEGER NOT NULL DEFAULT 0, -- 1: an expired grant, or a ceiling the call would pass
  first_seen     INTEGER NOT NULL,       -- unix seconds
  answered_at    INTEGER,                -- unix seconds; NULL is open
  answer         TEXT CHECK (answer IN ('grant', 'once', 'deny'))
);
CREATE UNIQUE INDEX IF NOT EXISTS origin_pending_open ON origin_pending (originator)
  WHERE answered_at IS NULL AND scope = 'wallet';

CREATE TABLE IF NOT EXISTS origin_spends (
  spend_id       INTEGER PRIMARY KEY,
  originator     TEXT NOT NULL,          -- the key
  month          TEXT NOT NULL,          -- YYYY-MM in UTC (WPM getCurrentMonthYearUTC)
  txid           TEXT,                   -- the signed path: CreateActionResult's txid; the deferred path: signAction's, once signed
  reference      TEXT,                   -- the deferred path: signableTransaction's reference as the wire carries it; NULL on the signed path
  satoshis       INTEGER NOT NULL,
  at             INTEGER NOT NULL,
  CHECK (txid IS NOT NULL OR reference IS NOT NULL)
);
CREATE INDEX IF NOT EXISTS origin_spends_month ON origin_spends (originator, month);
```

One grant row per (originator, scope), as the stack's machine keeps one row per origin and replaces it on a new grant (`step`'s `grant` arm, `lean/BrowserGate.lean` lines 160-163 at `4372ea39`): a grant is an upsert that sets `granted_at`, `expiry`, `amount` and `source`, and clears `revoked_at`; a revoke stamps `revoked_at` on the live row and deletes nothing. One open `wallet` pending row per originator (the reference's queue join; the machine's `addPending`); a spending pending row per call (the reference's unique spending key). An answer stamps `answered_at` and `answer` and keeps the row: the pending table is the history of the owner's prompts. `once` answers a `spending` row alone and is refused on a `wallet` row, as the client offers a one-time grant for a spend alone. A third table beyond the brief's two, `origin_spends`, holds the month's tally (`[W]` W7).

**The scopes, mapped to the doors.** Two scopes, `wallet` and `spending`:

| the owner's routes `/origins`, `/origins/answer`, `/origins/grant`, `/origins/revoke` (new, question 3) | no page ever | the owner's door, below; a page that could reach them could grant itself |
| the relay's `/health`, `/pull`, `/register` | outside the served doors | `bsv-wallet-relay`, its own binary and bearer |

**The spending scope's amount.** A call's amount is the sum of its requested outputs' satoshis, the measure the permission audit records (`satoshis` in `AuditEntry`, `src/server/audit.rs:35-52`). A live `spending` row admits the call when `amount` is NULL or the month's tally (`origin_spends`, this originator, this UTC month) plus the call's amount is at most `amount`. The check runs inside the `SpendingLock` (`src/server/mod.rs:42`), so two calls from one page cannot both pass a ceiling one of them fills; a call that needs the owner releases the lock while it waits and takes it again after the answer, then checks again. An admitted spend writes its `origin_spends` row after the toolbox returns the action; a failed call writes none. The row is keyed per flow, because bsv-rs's `CreateActionResult` carries a reference only inside `signableTransaction`, the unsigned template, and a signed action returns its `txid` (`src/wallet/types.rs:693-715` at bsv-rs `v0.9.0-beta.6`). On the signed path (`signAndProcess` true, `noSend` or not) the row holds the `txid` and a NULL `reference`. On the deferred path (`signAndProcess` false) it holds the reference as the handler serves it (`reference_string`, the base64 of the storage handle, `src/server/handlers.rs:431-437`, the same string a later `signAction` or `abortAction` names) and a NULL `txid`, and `signAction`'s answer fills the `txid`. Both columns are nullable and the table's `CHECK` refuses a row with neither. `abortAction` names one string, which the toolbox resolves as a reference and then as a txid (`find_transaction`, `src/storage/sqlx/abort_action.rs:490-508` at toolbox `v0.14.0-beta.6`). After the toolbox's abort succeeds, the row `WHERE originator = ? AND (reference = ?1 OR txid = ?1)` is deleted, so an aborted template and an aborted `noSend` action both leave the tally. A spend a broadcaster took is refused by the CLI's own pre-check (`retire_guard::abort_refused_for`, `src/server/handlers.rs:1022-1025`) and keeps its row.

**The key.** Every row's `originator` is PR 419's originator (`originator_of`, the `Origin`'s host lowercased with its port when named) with its port dropped, the reference's normalized hostname; the name with its port is `raw_originator`. The lookup is one indexed read on the hostname: PR 419's three-step lookup (`admits`, `src/server/origin_gate.rs:85-91`) collapses to it because every stored key is already a hostname, which is the reference's own rule (one grant covers every port of its host).

**Rules.** #411 rules 2 and 3; rule 23.5 (c) for the key, the expiry and the per-month spending ceiling. **Cost of a divergence.** Keying by the exact origin would split one host's grant by port and scheme against the reference and the owner's word of 2026-11-02; on-chain tokens (W2) would spend satoshis per grant and tie the gate to the broadcaster.

## (2) The pending answer

**The reference's answer.** The HTTP call is held open with no timer until the owner acts (above). A grant resolves it into the door's own answer; a deny answers `400 {"message": "Permission denied."}` (the grouped denial's text is `The user has denied the request for permission.`); a disconnect writes nothing to the caller and denies the prompt; the bridge's death or the server's shutdown answers `503 WALLET_BRIDGE_UNAVAILABLE`.

**The port's choice `[D]`, under rule 23.5 (c).** The gate (`gate`, `src/server/origin_gate.rs:245-266`, after the bearer and before the body, `src/server/mod.rs:349-362`) reads the originator's `wallet` row:

- **live**: admitted, logged as today (`browser gate: admitted`, with the row's `grant_id` and `source` in place of the env entry);
- **revoked**: refused at once, 400 `ERR_PERMISSION_DENIED`, `The user has denied the request for permission.` (`DENIED`), no pending row (the machine's `revoked`; `[W]` W3);
- **none, or expired**: the call joins the open `wallet` pending row or writes one (`renewal` 1 for an expired row), logged at info by name (`browser gate: pending`, `originator`, `call`, `pending_id`), and is **held**.

A held call waits, with no bound, for the earliest of: its row answered (`grant`: the call is judged again and goes on to its door; `deny`: 400 `ERR_PERMISSION_DENIED`, `Permission denied.`, the reference's per-request text: the client's protocol, basket and spending prompts deny through `denyPermission` ([ProtocolPermissionHandler:50](https://github.com/bsv-blockchain/bsv-desktop/blob/b791cb2b571d62f23256e97abf97557739278a49/src/lib/components/ProtocolPermissionHandler/index.tsx#L50), [BasketAccessHandler:21](https://github.com/bsv-blockchain/bsv-desktop/blob/b791cb2b571d62f23256e97abf97557739278a49/src/lib/components/BasketAccessHandler/index.tsx#L21)), whose error is `Permission denied.` ([WPM:1199](https://github.com/bsv-blockchain/ts-stack/blob/edf6e03dad39bd7bc4fc6e73e64de3a2b6f805c9/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts#L1199)), and the held call is the port's per-request prompt; the grouped text `DENIED` stays the revoked origin's, a refusal no prompt answered), the server's shutdown (503 `{"code": "WALLET_BRIDGE_UNAVAILABLE", "message": "WALLET_BRIDGE_UNAVAILABLE: HTTP server shutting down"}`, the client's code and text in the port's typed carrier, `[W]` W13), or the caller's disconnect (the connection's future is dropped: nothing is written, the door never runs). The wait reads its row every 250 ms (one indexed read; the CLI and the inspector are other processes) and wakes at once on the server's own answers (a `tokio::sync::Notify` per open row, signalled by the owner's routes). The shutdown is the server's `shutdown_signal` (`src/server/mod.rs:685`) passed to every waiter, because `with_graceful_shutdown` (`src/server/mod.rs:658`) waits for in-flight requests and a held call would otherwise hold the shutdown. A held call holds no lock: the gate runs before every handler and before the `SpendingLock`.

**The cap on pending rows and held calls `[D]`, `[W]` W14.** Without a cap, a hostile page could open any number of pending rows, one per subdomain (`a1.evil.example`, `a2.evil.example`, ...), each a separate key. That would flood the owner's prompt list with durable rows. Its held calls would also take the browser's six connections to the wallet's host, which every page on that browser shares. The reference has no cap: each originator opens its own prompt and each call waits. Its queue lives in memory and ends with the process, but here the rows outlast it. So the gate counts by registrable domain: the hostname's eTLD+1 under the Public Suffix List, compiled in by the `psl` crate (no network read; L5 adds it under `cargo deny`). An IP address or a single-label name such as `localhost` is its own domain. The limits:

- a registrable domain holds at most 4 open `wallet` pending rows and writes at most 4 new ones in any 60 s; the wallet holds at most 64 open `wallet` rows in all;
- a registrable domain has at most 2 held calls at once, and the wallet at most 4 in all (a spending call held inside `createAction` counts as one), which leaves at least 2 of the browser's six connections free for granted pages.

A call past any limit is answered at once and never held. The answer is 429 `{"code": "ERR_PERMISSION_PENDING_LIMIT", "message": "Too many permission requests from this site are waiting for the owner's answer."}` with `Retry-After: 5` and the CORS echo, so the page can read it. When the call's own originator already has an open row, it joins that row and writes nothing new. Otherwise no row is written. The refusal is logged at warn by name (`browser gate: pending limit`, `originator`, `domain`, `call`, the limit reached). The owner's answer to any row frees its places at once. A revoked origin is refused before the count, and a granted one is never counted.

A spending call is held the same way inside `createAction` after its `wallet` admission: its own pending row (`scope` `spending`, `amount`, `renewal` 1 when a live row's ceiling would be passed); `grant` (with an `amount` at least the tally plus the call) writes or replaces the `spending` row and the call is checked again; `once` admits that call alone and writes no grant (the reference's `ephemeral`); `deny` answers 400 `ERR_PERMISSION_DENIED`, `Permission denied.` (the reference's per-request denial, `denyPermission`).

The CORS answer moves to the client's: every answer to an `Origin` that parses carries its echo, the held call's included, so a page reads its grant's answer and its denial, as the client's `*` lets it (`setCorsHeaders`, [httpServer.ts:40-46](https://github.com/bsv-blockchain/bsv-desktop/blob/b791cb2b571d62f23256e97abf97557739278a49/electron/httpServer.ts#L40-L46)); every preflight from such an `Origin` is answered, since a page's opening `application/json` call must pass its preflight to write its pending row (`preflight`, `src/server/origin_gate.rs:272-290`, today refuses an unlisted one; `cors`, `src/server/origin_gate.rs:104-115`, echoes only a listed one). The echo stays an echo, never `*` (`allow_credentials` stays as PR 419 has it).

**The fixtures to record** (each in its own commit, under `docs/WIRE.md`'s rules): the held call granted (the door's 200 with the echo); the held call denied (400 `ERR_PERMISSION_DENIED`, `Permission denied.`, with the echo); the revoked call (400, at once, no pending row); the expired grant held and granted; the held call at shutdown (503 `WALLET_BRIDGE_UNAVAILABLE`); the spending call answered `once`, answered `grant` with a ceiling, and denied (`Permission denied.`). The recorder gains an owner step: a fixture names the owner's act (`{"owner": {"after_ms": 200, "answer": "grant"}}`), which the harness performs through the store module while the request is held. Fixture 180 (an unlisted origin's denial without the echo) and 181 (an unlisted preflight refused) move: under (c) an unknown origin is held, not refused, and its preflight is answered.

**Rules.** #411 rule 2 (the pending row and the client's shape), rule 4 (the bearer is checked ahead and never admits), 23.5 (c). **Cost of a divergence.** A bounded wait answering a refusal would break a page that waits on the owner as it waits on the client (the client removed its 30 s timer for this, [35cb5b6](https://github.com/bsv-blockchain/bsv-desktop/commit/35cb5b6)); refusing at once with a pending row (the machine's `pending` word read as a wire refusal) would make every page's opening call fail and need a retry the client never asks of it.

## (8) The charter transition's statement, for the keeper

"A door admits a page by the owner's grant for its origin." Over the rows, with `host(o)` the originator's hostname (the key) and `now` the call's time in seconds `[D]`:

```lean
-- A row is live for an origin and a scope at a time.
def live (gs : List Grant) (o : Origin) (s : String) (now : Time) : Bool :=
  gs.any (fun g => g.origin == host o && g.scope == s && g.revokedAt.isNone && !expired g now)

-- The door's predicate (every door but the exempt callback and the owner's routes).
-- `token`: the host holds a bearer token (`door`'s `token` argument at 4372ea39).
def admits (token : Bool) (r : Request) (gs : List Grant) (d : Door) : Prop :=
  (token = true → r.bearer = true) ∧
  ∃ o, r.origin = some o ∧ agrees r.claimed o = true ∧ live gs o "wallet" r.now = true ∧
    (d.spends = true → r.once = true ∨ ∃ g ∈ gs, g.origin = host o ∧ g.scope = "spending" ∧
       g.revokedAt = none ∧ (g.amount = none ∨ ∃ a, g.amount = some a ∧ r.spent + r.amount ≤ a))

-- The statement: an if-and-only-if. A call reaches door `d` exactly when `admits` holds.
theorem reaches_iff (token : Bool) (r : Request) (gs : List Grant) (d : Door) :
    (door token r gs d).admits = true ↔ admits token r gs d
```

It is an if-and-only-if, not an implication. The `→` direction says only a grant (and, for a spending door, a ceiling or a `once`) reaches a door; it is `admitted_only_by_live_grant` (line 238) lifted to scopes, with the bearer lock ahead. The `←` direction says a live grant, the bearer when one is set, and an agreeing claim are enough; it is `granted_admitted` (line 192), with the bearer and the spending clause added. The bearer clause is the lock in front of the gate (`door`, line 125): it can only refuse, so it appears as a conjunct and never as an alternative to the grant (`bearer_changes_no_word`, line 295).

What it asks of `lean/BrowserGate.lean` at `4372ea39`:

- `host : Origin → Origin`, the originator's hostname. At the pin `Origin` is already the hostname with its port dropped (line 43), so `host` is the identity there. It is named so the statement survives an `Origin` that keeps its port.
- `Door`, a structure with `spends : Bool` (`d.spends`), true for `createAction` alone. At the pin a door has no type: `door token r gs` (line 125) answers for every door alike, and gains the `Door` argument.
- `rowFor` keyed by (origin, scope) where it reads the origin alone (line 87).
- `Grant` gaining `amount : Option Nat`, and `Request` gaining `amount`, `spent` and `once` for the spending door.

Every existing theorem holds of the `wallet` scope unchanged, since the scenarios' rows are all scope `wallet`. The machine's `pending` and `expired` words are the host's held call on the wire (question 2); its `revoked` is the immediate refusal; `call_writes_no_grant` holds of the port because only the module's grant, answer, revoke and fold functions write `origin_grants`, and none is reachable from a page (question 3). The fold is an owner's act by configuration (the owner's `.env`), the machine's `grant` input with `source` `env`. Rule 8 is the keeper's: this is the statement the port builds to, not a change to the stack.
