# Lane oracle-hermetic: the e2e scenarios in CI without mainnet (#74)

**Repository.** `bsv-wallet-cli`, your worktree on a branch from `origin/beta`. `docs/lanes/README.md` binds you. Four hours.

**Read in this order.** #74 and the epic #106. `tests/e2e/run.js`, `tests/e2e/lib/setup.js`, `lib/wallet-client.js`, `lib/woc.js` (the harness: two wallets on 3370 and 3371 served by the release binary, funded by a funder daemon on 3320, the auditor asking three explorers), the 23 scenarios under `tests/e2e/scenarios/`. `src/services_env.rs` (every URL the binary reads: `CHAINTRACKS_URL`, `BANANABLOCKS_BASE`, the explorer keys), the toolbox's provider clients for the base URLs they take (`~/.cargo/registry/src/*/bsv-wallet-toolbox-rs-0.12.1/src/services/providers/*.rs`: WhatsOnChain, Bitails, BananaBlocks, ARC, chaintracks) and whether each base is configurable. The stack's rule 10 (`~/bsv/bsv-stack-lean/CLAUDE.md`): no network except reads; oracles run locally.

**The work.**
1. A stub service process, `tests/e2e/stub/` (Node, no new npm dependency beyond what `tests/e2e/package.json` has, or say what you need): one HTTP server that plays the header service (`/getPresentHeight`, `/findHeaderHexForHeight`, `/findChainTipHeaderHex`, the chain-feed SSE if the binary subscribes), the three explorers (the routes `src/explorers.rs` and the toolbox providers call: `/tx/{txid}`, `/tx/{txid}/beef`, `/tx/{txid}/hex`, `/txo/{txid}/{vout}`, the `/spent` route, the unspent and status routes), and a broadcaster (ARC's `/v1/tx` and `/v1/txs`, Arcade's shape if the binary uses it), over a recorded header chain and an in-memory mempool that accepts every well-formed transaction, "mines" a block on demand (`POST /_stub/mine`) and serves merkle paths for what it mined. Fault injection on demand (`POST /_stub/fault {provider, status, retryAfter, count}`) for the chaos suite later.
2. The harness runs hermetically when `E2E_HERMETIC=1`: the funder is a third stub-backed wallet the harness starts and seeds (the stub "mines" a coinbase-shaped funding to its address), every base URL points at the stub, the auditor asks the stub's explorers, nothing leaves the machine. Which scenarios pass as they are, which need a guard (say which and why; a scenario that cannot be hermetic is skipped under the flag with its reason printed, never silently).
3. A CI job `e2e-hermetic` in `.github/workflows/ci.yml` that builds the release binary, starts the stub, runs the harness under the flag, and uploads the kept directories on failure. Under four minutes on the Linux runner, or say what it takes and why.
4. `docs/E2E-HERMETIC.md`: the stub's routes, the flag, how to add a route when the binary learns a new one, what is not hermetic and why.

**Bounds.** No change under `src/` except a base-URL knob that a provider lacks, named in the report with the toolbox route it would need if the knob is the toolbox's (then `[D]` and a line for the stack keeper). `Cargo.toml` untouched. The mainnet harness unchanged in behaviour without the flag (run `node tests/e2e/run.js --dry-run` against nothing: it must refuse the same way as before). Never the funder on 3320, never a mainnet sat.

**Report.** `REPORT: STATUS done|blocked`, the base and tip commits, the scenarios' pass list under the flag, the CI job's time, the commands and their tails, every route the stub serves, the six tests each choice passes.
