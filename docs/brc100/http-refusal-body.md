BRC ID #: 100

Prepared for filing by Calhooon (owner). Draft only; no issue was created. This draft comes from a divergence between this wallet and the MetaNet Client that this wallet recorded in its wire fixtures ([Calhooon/bsv-wallet-cli#122](https://github.com/Calhooon/bsv-wallet-cli/issues/122), item 3).

BRC-100 gives every error one structure (`status`, `code`, `description`, optional `context`) and asks a parameter error to carry a code and a description naming the parameter, then leaves to each realisation "how these errors are communicated". Its own `### Error Handling` section specifies the binary substrate's frame (a one-byte error code, a message and an optional stack trace) and nothing for the HTTP JSON substrate. BRC-326 (Wallet Failure Presentation) builds on BRC-1's `description` and BRC-100's `{status, code, description}` envelope, adds `class`, `fault` and `retry`, leaves `code` to each wallet, and does not settle the HTTP body either. BRC-185 (Wallet Substrate Discovery), to which BRC-326 section 2.2 leaves transport failures, gives a stale binding on its HTTP RPC (`POST /brc185/v1/rpc/<method>`) a 412 with `PROVIDER_CHANGED`, carries an XDM error reply as `error: {code, message, data?}`, and types connection errors as `{domain, code, message, delivery}`; it states that "an explicit BRC-100 error remains the original wallet error" and gives no HTTP body for that error. The HTTP realisations answer differently, and a request the wallet cannot read (a body that does not parse, a required field missing) shows it most plainly. In the MetaNet Client a wallet call's failure is HTTP 400 with `{message}`: no code and no description (its one typed exception is the review-actions error of `createAction`, `signAction` and `internalizeAction`). The Client's bridge already answers its own refusals in the BRC's structure, `{status: "error", code, description}`: 503 `WALLET_LOCKED`, 503 `WALLET_BRIDGE_UNAVAILABLE` and 500 `HTTP_BRIDGE_ERROR`. Its other refusals take other shapes: 503 `{message}` while the wallet is not ready, 404 `{error}` for an unknown path, and 500 `{error}` from its outer catch. A body sent as JSON that does not parse never reaches its wallet; Express's default handler answers it with an HTML page (`express.json()` with no error middleware). The SDK's `HTTPWalletJSON` parses a refusal's body as JSON before it reads the status. It reads a typed error only from a 400 carrying `isError` and a numeric code it knows: 5 (review actions), 6 (`WERR_INVALID_PARAMETER`, with `parameter` and `message`) and 7 (insufficient funds). It turns any other refusal into `failed with HTTP status N` (a 400 carrying `isError` whose envelope fails its checks throws `Invalid wallet error envelope` or `Invalid <call> wallet error code` instead; code 5 is accepted only for `createAction` and `signAction`, so the Client's 400 review-actions error from `internalizeAction` is one deployed case), so a code or description the server sent in the BRC's structure is dropped, and a non-JSON body becomes a parse failure. The SDK therefore reads a third shape, `{isError, code: <number>, parameter, message}`, which is neither the BRC's structure nor the MetaNet Client's, and which neither the Client nor bsv-wallet-cli serves for a parameter error. Please specify the HTTP JSON substrate's refusal body: its members (the BRC's `code` and `description`, the deployed `message`, or the SDK's `{isError, code: <number>, parameter, message}` envelope), the status, and the answer for a request that does not parse or lacks a required parameter. This asks for a clarification of the transport; it does not claim that the BRC already requires one realisation's choice.

Vector (one request each; the BRC's structure, the MetaNet Client's answer as read from its source, this wallet's answer as recorded). Every request carries an `Origin` header: without one (or its `Originator` fallback) the Client answers 400 `{"message": "Origin header is required"}` before any call runs.
