# The nightly (#75, #76)

`.github/workflows/nightly.yml` runs on `workflow_dispatch` only (`gh workflow run nightly.yml --ref beta`). The owner's word (2026-10-27, #303): the Nightly is a waste of resources as a schedule (a scheduled night cost about twenty-five runner-hours, starved the pull requests' checks and read in the afternoon), so the measurement runs on dispatch: an incremental night on the captain's daily dispatch, the complete night at each pin and before each minor tag ([RELEASING.md](../RELEASING.md), step 4), and on demand (the two modes below, #462). It is not a PR gate (`ci.yml` is); it is the map of where the tests do not yet hold the machine. Two halves: fuzz targets on the bytes that come from outside, and mutation testing on the hot paths.

## The two modes (#462)

The owner's word of 2026-11-02, through the keeper ("even the nightly... is all that necessary? or maybe a fraction"): a file's mutation score moves only when the file or the tests that reach it change, so most nights need not mutate every file. The dispatch's input `mode` picks one of two nights.

- **Incremental** (the default: `gh workflow run nightly.yml --ref beta`). The job `plan` (`.github/nightly/changed_set.py`) diffs the night's tree against the last complete run's commit, which `docs/scoreboard/mutants.json` names (the record itself when its `mode` is `complete`, its `base` when `incremental`), and mutates only the floored files whose figure may have moved: a floored file that changed; every floored file a changed test reaches (a target the reach record of #401 measures reaches the floored files it ran a line of, so a left-out target reaches none; a target it does not measure, and a shared input such as `tests/wire/`, `tests/e2e/`, `fuzz/src/` or `fuzz/corpus/`, reaches every floored file, since no record yet names their reach per file); and the whole set when `Cargo.lock`, a workspace `Cargo.toml`, `nightly.yml` or the left-out list changed (a dependency bump counts as changing every file that uses it). Any other file under `src/` is read by the crate's module tree (each crate root's `mod` declarations, at their `#[path]`; #464's review): test-only code (declared under `#[cfg(test)]`, as `src/spend_gate/tests.rs` and its subdirectory are) reaches the floored file whose module tree holds it and every floored file a unit test that can run its lines can run, by the names the test files hold (`mod`, `use`, `a::b`, followed through each file they name); any other code (a module the lib or a binary compiles outside its tests, as `src/spend_gate/from.rs` or `src/config.rs`) brings in the whole set, the conservative choice, since a unit test under `--lib --bins` (in every shard) or a test target may run it beside any floored file and no record measures a unit test's reach per file. On this crate every floored file names the other four, so every changed `src/` Rust file outside the floored five brings in the whole set: an incremental night narrows for a change to the floored files alone, to a measured test target, or to the docs, the tools and CI. A non-Rust file under `src/` takes the effect of the source file that reads it by `include_str!`, and a `src/` file a test target compiles by `#[path]` is that target's input too. The keeper's risks (0.2 each) are that a test change reaches its files and a dependency every file; a floored file's own change still brings in that file alone, and the complete run at the next pin is the check on the rest. The shards deal the changed files' mutants at most 19 a shard (the complete night's sizing, 923 in fifty), in at least six shards while there are six mutants (the six runners a night holds at once, #144: a shard's wall clock is its baseline, about 11 minutes, and its own mutants) and never more than `MUTANTS_SHARDS`: one file alone is 6 shards for `explorers.rs` (30 mutants by the record) or `broadcast_verify.rs` (103), 9 for `server/handlers.rs` (168), 15 for `spend_gate.rs` (274), 19 for `tracker_host.rs` (348); the selection is the oracle's, unchanged (the owner's 23.9 word: complete per floored file). An empty set runs no shard: the night carries every figure and its summary says so. The hermetic pass judges the changed files' survivors alone, twenty a shard, at most six; no survivor, no hermetic shard. The fuzz targets run `FUZZ_SECONDS_INCREMENTAL` each (600 s, below), and the bench job only when the dispatch sets `bench`.
- **Complete** (`-f mode=complete`). Every floored file in twenty shards (`MUTANTS_SHARDS_COMPLETE`, the account's concurrent-job limit, #460), fourteen at a time, then six (the plan's `COMPLETE_PARALLEL`, #496, below), then the hermetic pass in six beside an hour a fuzz target, the reach job and the bench: the night of record, dispatched at each pin at the 03:00Z slot (RELEASING, step 4a), and the only night that may move a floor. An incremental night keeps its own sizing (#462): its changed files' shards, at most `MUTANTS_SHARDS_INCREMENTAL` (fifty, a whole set), six at a time.

**The carried-figure rule.** The score (`mutants_score.py --plan --record`) scores the plan's files from the night's outcomes and carries every other floored file's figure from the record's last complete run, its row reading `carried from run <id> at <sha>`; a carried figure is never judged against its floor again (its run judged it). Before any figure it refuses, naming the file: a carried figure whose base is not the last complete run (the record's entry names another run or sha, as an incremental night's own figure or an older run's does: such a figure is never carried again); a plan diffed against another base than the record's; on an incremental night, a floor of `MUTANTS_FLOORS` other than the record's `floors` (a floor moves only on a complete run, so a floor raised with its tests is judged by the next complete night, and incremental nights refuse until it); an outcome for a file outside the plan; and a complete plan short of a floored file. The night's record is the artifact `night-record`, the record's shape with `mode`, `base` and per file `{"source": "night"|"carried", "run", "sha"}`; the captain commits it over `docs/scoreboard/mutants.json` when the night is of record, and `tools/scoreboard` refuses a provenance that does not hold (a carried figure on a complete record, a carried figure from another run than the base, a night figure from another run than the record's) and renders a carried row's measured cell with its run.

**The fuzz budget.** An hour a target on a complete night; ten minutes (`FUZZ_SECONDS_INCREMENTAL`, 600 s) on an incremental one, proposed from the execution rates of run 41413946663 in `docs/scoreboard/fuzz.json` (an hour each): `allow_pending` 41,463 a second, `served_json` 32,571, `beef_reader` 3,494, `brc29_remittance` 592, `explorer_bodies` 3.45. Ten minutes is about 2,070 cases of the slowest target, more than its 18 seeds and that hour's 379 additions, and 355,000 of `brc29_remittance`'s.

**The cadence.** An incremental night on the captain's dispatch, the bench with it once a week (`-f bench=true`; #303 allows no schedule), the complete night at each pin.

**The fleet's stagger (#456).** The owner's word on the speed line (2026-11-02, through the keeper): the fleet's nightlies are staggered so that they never share the account's runner limit with each other or with the day's landings. Each repository's night has its own slot of about three hours: bsv-rs at 00:00Z, this repository's Nightly at 03:00Z, the toolbox at 06:00Z. The day's `workflow_dispatch` runs, including the captain's, stay off 00:00Z to 09:00Z unless the keeper names a free slot. The reason is the account's runner limit, which the fleet's nights and the day's landings share: the third night, run 41516017523, was dispatched on `beta` at 20:05Z and was still at 9 of its 50 shards after two hours behind the day's landings. This workflow has no `schedule` line (#303 above), so the 03:00Z slot is the time to dispatch it. The captain dispatches this repository's night at the fleet's 03:00Z slot (`gh workflow run nightly.yml --ref beta` at that hour), never inside bsv-rs's 00:00Z window or the toolbox's 06:00Z window, and the first dispatch after a record's landing waits for the next 03:00Z; #303's word stands (no schedule, dispatch only). A cron line would reverse #303 and needs the owner's word. It would also fire only from the default branch, `main`, at `main`'s commit.

**One night at a time; a complete night in two waves (#144, #460, #496).** The workflow's concurrency group is the one name `nightly` (never one per ref: a dispatch runs the ref it names, so a per-ref group would let runs on two refs go side by side), with `cancel-in-progress: false`: a night started while one runs waits for it and is never cut short. The dispatched night of 2026-10-24 (run 40074725488) started all twenty shards and the five fuzz targets together, held every runner for over an hour and starved every PR check, so the matrix ran six at a time (`max-parallel: 6`); at fifty shards (#310) a complete night then queued for eight to ten hours (the wall clock below). The owner's words of 2026-11-02 (through the keeper: no own hardware, no paid runners) size the complete night to the account instead: twenty shards, the account's concurrent-job limit, at the fleet's 03:00Z slot (#456 above), when the day's landings are off the account. They run fourteen at a time, then six (#496): the plan's `parallel`, which the matrix's `max-parallel` reads, is `COMPLETE_PARALLEL` in `.github/nightly/changed_set.py`, the account's concurrent-job limit (`ACCOUNT_RUNNERS`, 20) less a PR run's six jobs (`PR_RUN_JOBS`: lint, Build, Test, vectors, wire, e2e-hermetic; `changes` is seconds), and never more than the plan's count. The keeper's fleet line of 06:2xZ on 2026-11-03: the account's twenty runners are one pool across four repositories, and every scheduled or dispatched heavy run carries max-parallel 14, so six runners stay for PR and queue runs fleet-wide; 14 is the number until a later row reads the limit from the API. The figure (#496): under night 3 (run 41516017523, fifty shards holding all twenty runners until 05:48:21Z) the PR runs of 11-03 took 47 and 55 minutes end to end for about 5 minutes of their jobs' work (runs 41582262307 and 41580928455), against 5 minutes in the empty hour before; a PR run keeps its six runners and its five minutes. The cost is the second wave: a complete night about two hours longer (its longest shard of the six). The fuzz targets, the reach job and the bench wait for the matrix (`needs: [plan, mutants]`, run whatever it concluded, never without a plan), so no shard waits for them; they run beside the hermetic pass's six once the matrix ends, thirteen jobs at most. An incremental night keeps six at a time and the same order.

## The fuzz targets

`fuzz/` is a `cargo-fuzz` crate with its own manifest, workspace and `Cargo.lock`; the root `Cargo.toml` does not name it. Each target runs the night's budget (an hour on a complete night, ten minutes on an incremental one, the two modes above) on the corpus under `fuzz/corpus/<target>/`. The jobs' rustc is the dated nightly `FUZZ_NIGHTLY` at the top of `nightly.yml` (#395: the unpinned channel's rustc of 2026-10-31 refused sqlx-core 0.8.6 with E0391 and no target built); the pin moves by PR when a newer nightly is proven to build and run the five targets, never by drift.

| target | the bytes | what may not happen |
|---|---|---|
| `beef_reader` | the AtomicBEEF and BEEF bytes the server consumes, through the reads it makes: `internalizeAction`'s subject (`post_word::atomic_subject`), the toolbox wallet's pre-store parse, the toolbox store's step 1 (streaming reader, parse, atomic txid, structure check, the subject's outputs), `createAction`'s AtomicBEEF build and unproven ancestors, `receive`'s courier (`src/atomic_beef.rs`, compiled into the target by `#[path]`) | a panic; an atomic txid the door's subject disagrees with; an AtomicBEEF the CLI writes that it cannot read back |
| `brc29_remittance` | the internalize arguments of a BRC-29 payment (derivation prefix and suffix, sender identity key, output index, the carrying transaction), through `server::handlers::internalize_args` and the toolbox wallet's derivation checks | a panic; a field changed by the mapping; an empty derivation, an index past the outputs, or a payment to another key taken; a payment to the derived key refused |
| `served_json` | a `/createAction` or `/internalizeAction` body: the lenient-JSON layer (`server::sanitize_lone_surrogates`), serde into the MetaNet Client shapes, the handlers' argument mappings (`server::handlers::create_action_args`, `internalize_args`) | a panic; a sanitizer that is not idempotent; a caller's rule label surviving the internalize mapping |
| `explorer_bodies` | each explorer body the CLI still reads itself: `receive`'s couriers (WhatsOnChain's `/beef`, BananaBlocks' `/hex`, by `Explorers::at`'s calls) and the broadcast verifier's chain indexes (WhatsOnChain and Bitails by `BroadcastVerifier::single_pass` with BananaBlocks off, since its provider is a process-wide cell the first case would fix; BananaBlocks by `BroadcastVerifier::explicit` and `with_bananablocks`, a fresh provider at a turning base each case), served with a fuzzed status from a local socket; the spender rungs left in 0.18.2 (#196) | a panic; a courier's delivery from a non-200, WhatsOnChain's BEEF other than the body's hex, BananaBlocks' bytes that do not hash to the txid; a chain index present from anything but its 200, absent from anything but its 404, `Rejected` from neither, `Mined` without its field; BananaBlocks' `mined` or `known` for a body about another transaction, or its silence standing against the voting index's 404 |
| `allow_pending` | `allowPending` as the door and the commands read it (`AllowPending::from_json`, `from_cli`, `parse_outpoint`) | a panic; an empty, unsorted or repeated scope; a scope that does not reach a coin it names; an outpoint that does not print back to itself |

**The properties on stable (#396).** Each target's body is a function of the crate's library, `fuzz/src/props/<target>.rs`, and the target calls it and nothing else (`fuzz_target!(|data: &[u8]| check(data))`; `brc29_remittance` takes its structured `Input`, which the library defines). No item of the library names `libfuzzer-sys`, so the package's `tests/fuzz_replay.rs` compiles `fuzz/src/lib.rs` by `#[path]` on stable and passes every file of each target's committed seed corpus through the same function (`brc29_remittance`'s bytes decoded as libfuzzer-sys decodes them, with the fuzz lock's `arbitrary`, a dev-dependency pinned to its version); a missing or empty corpus, a target without its replay, or a seed the binary would reject fails by name. It runs in well under a second and is a cargo test target like any other, so the mutation oracle runs it (below). The Nightly's corpus artifacts are not replayed: they are a night's run artifacts, not the tree's.

**The mirror.** The served doors' mappings are functions the targets call (`create_action_args`, `internalize_args`), so no copy of the CLI's code drifts. One step stays a copy, because it is written inline in the toolbox's async `Wallet::internalize_action` and cannot be called without a wallet and a store: `fuzz/src/lib.rs` `internalize_precheck` (bsv-wallet-toolbox-rs 0.14.0-beta.1, the derivation checks, unchanged from 0.13.0) names the lines it copies. It drifts when the toolbox's source changes; the cure is a function in the toolbox the target calls.

**The crate's pins and its check (#301).** `fuzz/` is its own workspace with its own `Cargo.lock`, so no root build touches it. Its bsv-rs and toolbox pins are the root `Cargo.toml`'s exact pins, moved with them in every pin PR and its lock regenerated (`cargo update --manifest-path fuzz/Cargo.toml -w`): on beta.1 they were left behind, two bsv-rs crates met in the fuzz graph and `brc29_remittance` stopped building. The lock also records the CLI's own version, so a version bump (a release PR) refreshes it the same way, or the check below refuses the stale lock. CI holds it on every PR: the `build` job runs `cargo check --manifest-path fuzz/Cargo.toml --locked --all-targets` on the pinned toolchain (libfuzzer-sys checks on stable), so a target that stops compiling fails the PR that broke it; the `locks` job finds one bsv-rs in each committed lock and, in every lock but the root's, bsv-rs, the toolbox and bsv-tracker at the root lock's versions.

**Locally.** `cargo +nightly fuzz run <target> <scratch-dir> fuzz/corpus/<target> -- -max_total_time=300` from the checkout's root (the scratch directory before the seeds, so new entries land there and not in the seeds). The targets build in release without debug assertions, as the shipped binary does. `cargo run --example seed_corpus` from `fuzz/` rewrites the seeds from the shapes the tests and e2e scenarios use.

## Where the results land

- **The run's summary**: each fuzz job's libFuzzer statistics in its log and the number of corpus additions in the job summary; the mutation table in the `Mutation score` job's summary.
- **Corpus growth**: the entries of the hour that add coverage beyond the checked-in corpus (libFuzzer's `-merge=1`) are the artifact `corpus-<target>`, kept 30 days. The repository does not let Actions open pull requests, so the workflow cannot; whoever lands the night's growth downloads the artifacts (`gh run download <run> -p 'corpus-*'`), copies each into `fuzz/corpus/<target>/` and opens one PR, corpus only.
- **The fuzz record (#445)**: `docs/scoreboard/fuzz.json`, the scoreboard's fuzz rows, is `tools/fuzz-record <run>`'s output, never typed. The tool reads the run with `gh`: the five `Fuzz (<target>)` jobs, each job's log (`gh run view <run> --job <job> --log`) and the `corpus-*` and `crash-*` artifacts. Each target's seconds and executions come from libFuzzer's one `Done <runs> runs in <s> second(s)` line, whose runs must equal `stat::number_of_executed_units`. Its corpus additions come from the merge step's one `corpus additions: <n>` line, which must equal the `corpus-<target>` artifact's file count. Its crashes are the `crash-<target>` artifact's stopping inputs, which must match the log's `Test unit written to` lines. The record's date is the run's creation day (UTC). The tool refuses the night and writes nothing, naming each target at fault, when the jobs are not `fuzz/Cargo.toml`'s targets, a job did not succeed, a job checked out another commit than the run's (a night is one tree, #423), the jobs' rustc differ, or a figure is missing, repeated or contradicted by its witness. It prints each target's figures with its job, commit and rustc. `--keep <dir>` writes what it read (the run, the logs and the artifact listing) to a new directory; `--from <dir>` recomputes the record from that directory without the network. A reviewer runs the tool on the same run and `diff`s the result against the committed file, as `tools/bench-compare --append` and `mutants_score.py` are recomputed. Its test (`tools/test_fuzz_record.py`, in CI's scoreboard step) feeds `tools/testdata/fuzz-record/41413946663`, an excerpt of run 41413946663's logs and its artifact listing, and expects the exact record. After it writes a record, `python3 -B tools/scoreboard --render` updates the fuzz rows.
- **Mutation outcomes**: each shard's `outcomes.json`, `missed.txt`, the mutants' diffs and `sha` (the commit it ran on, #423) are the artifact `mutants-<shard>`.

## What a crash input becomes

A target that stops (a panic, a failed property, a timeout, out of memory) and leaves its input (libFuzzer's `crash-`, `timeout-`, `oom-` or `leak-` file) fails its job, uploads the input as `crash-<target>` (kept 90 days), and opens an issue titled `Nightly fuzz: <target> crashed` with each input in base64 in the body (an issue takes no file; an input over 16 KB is cut to its first 16 KB there and says so, the whole input in the artifact), the log's tail and the run's link; a crash on a target with that issue open comments on it. A non-zero exit with no input (the target did not build, cargo-fuzz failed) is not a crash: the job fails with that word and no issue is opened. The fix lands with the input as a regression: the input added to `fuzz/corpus/<target>/` and, where the bytes are the wallet's to judge, a unit test on the reader that crashed. A crash in a BEEF reader is a witness scenario for the stack's beef-of-any-size charter.

## The mutation score and what a surviving mutant becomes

`cargo-mutants` (copy mode, never `--in-place`) mutates `src/spend_gate.rs`, `src/tracker_host.rs`, `src/server/handlers.rs`, `src/broadcast_verify.rs` and `src/explorers.rs`, on a complete night in twenty shards dealt round-robin (#460); a mutant's tests stop at twice its shard's baseline (the oracle below). `.github/nightly/mutants_score.py` scores each file as caught / (caught + missed + timeout): a timeout has its own column and is not caught (its tests ran past the limit, which no test's verdict showed wrong; it weighs as a miss does), and an unviable mutant (one that does not build) is counted nowhere, and fails the job when a file is below its floor or has no outcome. The target is 80 percent a file. A measured floor only rises: a file's floor is the score a night measured, rounded down, named in the workflow with the issue that raises it, and it is raised in the same commit as the tests that earn the raise, never by an edit alone. A floor set before any night measured its file was provisional; the first full night replaced those with what it measured. A floor is measured when `docs/scoreboard/mutants.json` names its file and provisional when it does not. `tools/scoreboard` holds the floors' rule, numbered as in its header:

1. **The ceiling.** A measured floor is never above its file's score rounded down, whether it rose, stayed, fell or is new. It is the tree's alone, so every `tools/scoreboard --check` holds it for every floor of `MUTANTS_FLOORS`, with a base or without one (CI on a push whose previous commit cannot be fetched), and a fault names the file, the floor and the score. The owner's word of 2026-11-01: "if the complete oracle's figure for a file comes out under its floor, the Nightly goes red by design and the captain opens the issue; never lower a floor to pass." The one exception (#310): a floor may stand above its measured score when `docs/scoreboard/mutants.json`'s `verdict` holds that file below its floor and names its open issue (`red by design: <file> <score> below its floor <floor>; .. #N`), and `--check` then prints the file as RED BY DESIGN with the issue and does not fail on it, while a verdict without the issue or on a file at or above its floor fails naming the file.
2. **The fall** (`--check --base`, the CI job `ratchet`). A floor with a measurement at the base never falls; a provisional floor never falls without a measurement in the tree's record; a measurement at the base never vanishes from the tree.
3. **The first measurement** (`--base`). A provisional floor at the base whose file the tree's record measures may fall once, and then to exactly its score rounded down, never lower (and by 1 never higher), with a notice naming the file and both floors.
4. **The provisional notice.** A floor with no measurement is allowed as provisional and held to no score; every `--check` prints a notice naming it.

**The oracle, the limit and the exit code (#310).** A floored file's oracle is every test target that runs a line of it, whole: the step passes `cargo test` the library's and the binaries' unit tests (`--lib --bins`) and a `--test` for every target under `tests/`, a target added later joining by itself, and skips no test inside a target; the selection is how the baseline runs, never the oracle's ceiling (the owner's word of 2026-11-01). It leaves out only the twelve targets listed in `.github/nightly/no-floored-targets`, each of which runs no line of the five files under coverage and starts no process (`cargo llvm-cov` per target at `6e7b738`): the eight `arch_*` scanners and `rule_28_sites` read the source as text, `brc100` reads the committed fixtures, `header_source` and `signing_digest_vector` call other modules. `serve_bind_guard` also reads no line, but its served case kills the binary it starts and a killed process leaves no coverage, so it stays. The benches run too, each routine once in criterion's test mode with its assertions (`--bench`, a bench added later joining by itself): `gate_assess` and `create_action_signed` run lines of `spend_gate.rs` and `tracker_host.rs`, while `internalize_action` (only `server/post_word.rs`) and `list_outputs` run no line of the five, so the list leaves them out too (`cargo llvm-cov --bench` per bench at `cd53740`). Every floored file is reached by `wire` (the replay through the router), so no file's oracle is smaller than the slowest target's run and the five share one selection. The package has no doctest. Since #400 the binary takes `broadcast_verify`, `explorers` and `server` from the library rather than declaring them again, so their unit tests run once, in `--lib`, where they ran in both `--lib` and `--bins` before; the oracle loses no test. The whole oracle's baseline ran past the old fixed 300 s on every shard of run 41253247135 (no mutant was tested), so the limit is no fixed `--timeout`: the baseline always runs (never `--baseline skip`, which lets a broken tree read as every mutant caught), bounded only by the job's 340 minutes, and each mutant's tests stop at twice the shard's measured baseline (`--timeout-multiplier 2`, printed as "Auto-set test timeout"); each shard prints its selection before it runs. The step reads cargo-mutants 27.1.0's exit code: 0 (every mutant caught), 2 (a mutant missed) and 3 (a test timed out) go on to the score job, which judges them; 4 (the unmutated baseline failed, no mutant tested), 1 (a usage error) and any other code fail the shard, so an empty `outcomes.json` never ends a shard green.

**The left-out targets are guarded, not trusted by name (#401).** The fourteen left-out entries (the twelve test targets and the two benches above) live in one file, `.github/nightly/no-floored-targets`, one `test <name>` or `bench <name>` a line; the selection step reads it (`.github/nightly/no_floored.py list test|bench`) and so does the guard, and no other copy of the names exists. The rule: a left-out target runs no line of a floored file (a file of `MUTANTS_FLOORS`); one that comes to run one judges that file, so it joins the oracle and leaves the list. Two halves hold it. The Nightly's job `mutants-reach` (one runner, beside the shards) runs `no_floored.py measure`: `cargo llvm-cov --locked --lcov` once per entry on the night's tree, failing by the entry's kind, its name and the first floored line it ran, and failing too when a report never names a floored file (its reach is unread, never zero); the score refuses a night whose reach job did not succeed, and the job's artifact `no-floored-reach` is the night's record. CI's ratchet job runs `no_floored.py check` on the committed record `.github/nightly/no-floored-reach.json`, which fails, naming each, on an entry the record does not measure, a record entry off the list, an entry that names no target, a floored file the record does not measure, and an entry recorded with reach; so a PR that adds an entry, or a floored file, brings its measurement (`python3 -B .github/nightly/no_floored.py measure .github/nightly/no-floored-reach.json` on its tree, or the night's artifact). The record at `678a9ff`: every entry 0 lines of all five files. The refusal's form, one line per entry with reach and then the count, exit 1: `::error::<kind> <name> runs <floored file>:<first line> and <n> more of its lines: it judges a floored file, so it joins the oracle; take it out of .github/nightly/no-floored-targets`, then `measure: <k> fault(s); the left-out targets' zero reach does not hold` (`check` the same, as `check:`). Shown on a planted call (2026-11-02, never pushed): on a scratch branch from `5c7ffe2`, one line in `tests/header_source.rs`, `assert!(bsv_wallet_cli::spend_gate::allow_pending(Some("received")));`, and the job's command (`python3 -B .github/nightly/no_floored.py measure out/no-floored-reach.json`, cargo-llvm-cov 0.6.14) measured the fourteen in 320 s and exited 1 with `::error::test header_source runs src/spend_gate.rs:343 and 2 more of its lines: it judges a floored file, so it joins the oracle; take it out of .github/nightly/no-floored-targets`, every other entry at 0.
