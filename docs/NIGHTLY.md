# The nightly (#75, #76)

`.github/workflows/nightly.yml` runs on `workflow_dispatch` only (`gh workflow run nightly.yml --ref beta`). The owner's word (2026-10-27, #303): the Nightly is a waste of resources as a schedule (a scheduled night cost about twenty-five runner-hours, starved the pull requests' checks and read in the afternoon), so the measurement runs on dispatch, one before each minor tag, none for a prerelease, and on demand. It is not a PR gate (`ci.yml` is); it is the map of where the tests do not yet hold the machine. Two halves: fuzz targets on the bytes that come from outside, and mutation testing on the hot paths.

**One night at a time, six shards at a time (#144).** The workflow's concurrency group is the one name `nightly` (never one per ref: a dispatch runs the ref it names, so a per-ref group would let runs on two refs go side by side), with `cancel-in-progress: false`: a night started while one runs waits for it and is never cut short. The mutants matrix runs at most six of its twenty shards at once (`max-parallel: 6`). The dispatched night of 2026-10-24 (run 40074725488) started all twenty shards and the five fuzz targets together, held every runner for over an hour and starved every PR check; its shards took about 1,160 runner-minutes, so at six a night's mutants take near three and a half hours, and the night peaks at eleven runners (six shards beside the five fuzz targets' hour) and holds six after it.

## The fuzz targets

`fuzz/` is a `cargo-fuzz` crate with its own manifest, workspace and `Cargo.lock`; the root `Cargo.toml` does not name it. Each target runs one hour a night on the corpus under `fuzz/corpus/<target>/`. The jobs' rustc is the dated nightly `FUZZ_NIGHTLY` at the top of `nightly.yml` (#395: the unpinned channel's rustc of 2026-10-31 refused sqlx-core 0.8.6 with E0391 and no target built); the pin moves by PR when a newer nightly is proven to build and run the five targets, never by drift.

| target | the bytes | what may not happen |
|---|---|---|
| `beef_reader` | the AtomicBEEF and BEEF bytes the server consumes, through the reads it makes: `internalizeAction`'s subject (`post_word::atomic_subject`), the toolbox wallet's pre-store parse, the toolbox store's step 1 (streaming reader, parse, atomic txid, structure check, the subject's outputs), `createAction`'s AtomicBEEF build and unproven ancestors, `receive`'s courier (`src/atomic_beef.rs`, compiled into the target by `#[path]`) | a panic; an atomic txid the door's subject disagrees with; an AtomicBEEF the CLI writes that it cannot read back |
| `brc29_remittance` | the internalize arguments of a BRC-29 payment (derivation prefix and suffix, sender identity key, output index, the carrying transaction), through `server::handlers::internalize_args` and the toolbox wallet's derivation checks | a panic; a field changed by the mapping; an empty derivation, an index past the outputs, or a payment to another key taken; a payment to the derived key refused |
| `served_json` | a `/createAction` or `/internalizeAction` body: the lenient-JSON layer (`server::sanitize_lone_surrogates`), serde into the MetaNet Client shapes, the handlers' argument mappings (`server::handlers::create_action_args`, `internalize_args`) | a panic; a sanitizer that is not idempotent; a caller's rule label surviving the internalize mapping |
| `explorer_bodies` | each explorer body the CLI still reads itself: `receive`'s couriers (WhatsOnChain's `/beef`, BananaBlocks' `/hex`, by `Explorers::at`'s calls) and the broadcast verifier's chain indexes (WhatsOnChain and Bitails by `BroadcastVerifier::single_pass` with BananaBlocks off, since its provider is a process-wide cell the first case would fix; BananaBlocks by `BroadcastVerifier::explicit` and `with_bananablocks`, a fresh provider at a turning base each case), served with a fuzzed status from a local socket; the spender rungs left in 0.18.2 (#196) | a panic; a courier's delivery from a non-200, WhatsOnChain's BEEF other than the body's hex, BananaBlocks' bytes that do not hash to the txid; a chain index present from anything but its 200, absent from anything but its 404, `Rejected` from neither, `Mined` without its field; BananaBlocks' `mined` or `known` for a body about another transaction, or its silence standing against the voting index's 404 |
| `allow_pending` | `allowPending` as the door and the commands read it (`AllowPending::from_json`, `from_cli`, `parse_outpoint`) | a panic; an empty, unsorted or repeated scope; a scope that does not reach a coin it names; an outpoint that does not print back to itself |

**The mirror.** The served doors' mappings are functions the targets call (`create_action_args`, `internalize_args`), so no copy of the CLI's code drifts. One step stays a copy, because it is written inline in the toolbox's async `Wallet::internalize_action` and cannot be called without a wallet and a store: `fuzz/src/lib.rs` `internalize_precheck` (bsv-wallet-toolbox-rs 0.14.0-beta.1, the derivation checks, unchanged from 0.13.0) names the lines it copies. It drifts when the toolbox's source changes; the cure is a function in the toolbox the target calls.

**The crate's pins and its check (#301).** `fuzz/` is its own workspace with its own `Cargo.lock`, so no root build touches it. Its bsv-rs and toolbox pins are the root `Cargo.toml`'s exact pins, moved with them in every pin PR and its lock regenerated (`cargo update --manifest-path fuzz/Cargo.toml -w`): on beta.1 they were left behind, two bsv-rs crates met in the fuzz graph and `brc29_remittance` stopped building. The lock also records the CLI's own version, so a version bump (a release PR) refreshes it the same way, or the check below refuses the stale lock. CI holds it on every PR: the `build` job runs `cargo check --manifest-path fuzz/Cargo.toml --locked --all-targets` on the pinned toolchain (libfuzzer-sys checks on stable), so a target that stops compiling fails the PR that broke it; the `locks` job finds one bsv-rs in each committed lock and, in every lock but the root's, bsv-rs, the toolbox and bsv-tracker at the root lock's versions.

**Locally.** `cargo +nightly fuzz run <target> <scratch-dir> fuzz/corpus/<target> -- -max_total_time=300` from the checkout's root (the scratch directory before the seeds, so new entries land there and not in the seeds). The targets build in release without debug assertions, as the shipped binary does. `cargo run --example seed_corpus` from `fuzz/` rewrites the seeds from the shapes the tests and e2e scenarios use.

## Where the results land

- **The run's summary**: each fuzz job's libFuzzer statistics in its log and the number of corpus additions in the job summary; the mutation table in the `Mutation score` job's summary.
- **Corpus growth**: the entries of the hour that add coverage beyond the checked-in corpus (libFuzzer's `-merge=1`) are the artifact `corpus-<target>`, kept 30 days. The repository does not let Actions open pull requests, so the workflow cannot; whoever lands the night's growth downloads the artifacts (`gh run download <run> -p 'corpus-*'`), copies each into `fuzz/corpus/<target>/` and opens one PR, corpus only.
- **Mutation outcomes**: each shard's `outcomes.json`, `missed.txt` and the mutants' diffs are the artifact `mutants-<shard>`.

## What a crash input becomes

A target that stops (a panic, a failed property, a timeout, out of memory) and leaves its input (libFuzzer's `crash-`, `timeout-`, `oom-` or `leak-` file) fails its job, uploads the input as `crash-<target>` (kept 90 days), and opens an issue titled `Nightly fuzz: <target> crashed` with each input in base64 in the body (an issue takes no file; an input over 16 KB is cut to its first 16 KB there and says so, the whole input in the artifact), the log's tail and the run's link; a crash on a target with that issue open comments on it. A non-zero exit with no input (the target did not build, cargo-fuzz failed) is not a crash: the job fails with that word and no issue is opened. The fix lands with the input as a regression: the input added to `fuzz/corpus/<target>/` and, where the bytes are the wallet's to judge, a unit test on the reader that crashed. A crash in a BEEF reader is a witness scenario for the stack's beef-of-any-size charter.

## The mutation score and what a surviving mutant becomes

`cargo-mutants` (copy mode, never `--in-place`) mutates `src/spend_gate.rs`, `src/tracker_host.rs`, `src/server/handlers.rs`, `src/broadcast_verify.rs` and `src/explorers.rs` in fifty shards dealt round-robin; a mutant's tests stop at twice its shard's baseline (the oracle below). `.github/nightly/mutants_score.py` scores each file as caught / (caught + missed + timeout): a timeout has its own column and is not caught (its tests ran past the limit, which no test's verdict showed wrong; it weighs as a miss does), and an unviable mutant (one that does not build) is counted nowhere, and fails the job when a file is below its floor or has no outcome. The target is 80 percent a file. A measured floor only rises: a file's floor is the score a night measured, rounded down, named in the workflow with the issue that raises it, and it is raised in the same commit as the tests that earn the raise, never by an edit alone. A floor set before any night measured its file was provisional; the first full night replaced those with what it measured. A floor is measured when `docs/scoreboard/mutants.json` names its file and provisional when it does not. `tools/scoreboard` holds the floors' rule, numbered as in its header:

1. **The ceiling.** A measured floor is never above its file's score rounded down, whether it rose, stayed, fell or is new. It is the tree's alone, so every `tools/scoreboard --check` holds it for every floor of `MUTANTS_FLOORS`, with a base or without one (CI on a push whose previous commit cannot be fetched), and a fault names the file, the floor and the score.
2. **The fall** (`--check --base`, the CI job `ratchet`). A floor with a measurement at the base never falls; a provisional floor never falls without a measurement in the tree's record; a measurement at the base never vanishes from the tree.
3. **The first measurement** (`--base`). A provisional floor at the base whose file the tree's record measures may fall once, and then to exactly its score rounded down, never lower (and by 1 never higher), with a notice naming the file and both floors.
4. **The provisional notice.** A floor with no measurement is allowed as provisional and held to no score; every `--check` prints a notice naming it.

**The oracle, the limit and the exit code (#310).** A floored file's oracle is every test target that runs a line of it, whole: the step passes `cargo test` the library's and the binaries' unit tests (`--lib --bins`) and a `--test` for every target under `tests/`, a target added later joining by itself, and skips no test inside a target; the selection is how the baseline runs, never the oracle's ceiling (the owner's word of 2026-11-01). It leaves out only the twelve targets the step names in `NO_FLOORED_CODE`, each of which runs no line of the five files under coverage and starts no process (`cargo llvm-cov` per target at `6e7b738`): the eight `arch_*` scanners and `rule_28_sites` read the source as text, `brc100` reads the committed fixtures, `header_source` and `signing_digest_vector` call other modules. `serve_bind_guard` also reads no line, but its served case kills the binary it starts and a killed process leaves no coverage, so it stays. The benches run too, each routine once in criterion's test mode with its assertions (`--bench`, a bench added later joining by itself): `gate_assess` and `create_action_signed` run lines of `spend_gate.rs` and `tracker_host.rs`, while `internalize_action` (only `server/post_word.rs`) and `list_outputs` run no line of the five, so the step's `NO_FLOORED_BENCHES` leaves them out (`cargo llvm-cov --bench` per bench at `cd53740`). Every floored file is reached by `wire` (the replay through the router), so no file's oracle is smaller than the slowest target's run and the five share one selection. The package has no doctest. The whole oracle's baseline ran past the old fixed 300 s on every shard of run 41253247135 (no mutant was tested), so the limit is no fixed `--timeout`: the baseline always runs (never `--baseline skip`, which lets a broken tree read as every mutant caught), bounded only by the job's 340 minutes, and each mutant's tests stop at twice the shard's measured baseline (`--timeout-multiplier 2`, printed as "Auto-set test timeout"); each shard prints its selection before it runs. The step reads cargo-mutants 27.1.0's exit code: 0 (every mutant caught), 2 (a mutant missed) and 3 (a test timed out) go on to the score job, which judges them; 4 (the unmutated baseline failed, no mutant tested), 1 (a usage error) and any other code fail the shard, so an empty `outcomes.json` never ends a shard green.

**Judges outside the cargo oracle.** The five fuzz targets of `fuzz/` carry property assertions over floored files, but they live in their own workspace under nightly rustc, which the package's `cargo test` cannot build, so no mutant is judged by them: `allow_pending` reaches `spend_gate.rs`; `served_json` and `brc29_remittance` reach `server/handlers.rs` (`served_json` also `spend_gate::rule_of_label`); `explorer_bodies` reaches `broadcast_verify.rs` and `explorers.rs`; `beef_reader` reaches the server's `post_word` (not a floored file itself). The shape that brings their assertions in, a stable-toolchain cargo test target replaying each target's committed seed corpus through the same property function, is #396, the captain's to decide. The hermetic e2e suite was the other judge outside the oracle; since #393 it is in it, as the second pass below.

**A night is judged whole (#310).** Fifty shards, max-parallel six (#144), mutant `i` on shard `i % 50` (`--sharding round-robin`). The missed mutants lie in runs of the list, so consecutive slices gather them into one shard. At the last scheduled night's outcome mix (run 40473522272, mapped onto today's 1,191 mutants) and the oracle's baseline of 721 s with the benches in (this Mac, loaded), the worst shard with ten timeouts takes 461 minutes as forty slices, 517 as fifty slices, 363 as forty dealt round-robin and 330 as fifty dealt round-robin, the one shape under the job's 340 minutes; the night is about 56 runner-hours, about nine hours at six at a time. A shard writes a success marker only after cargo-mutants ends with 0, 2 or 3, and the score job refuses to judge, naming each shard without its marker, unless the matrix concluded success: a shard cut at its limit, failed or cancelled still uploads its partial `outcomes.json` for the evidence, and a partial night is never scored.

**The hermetic pass and the union (#393).** The hermetic e2e suite (`E2E_HERMETIC=1 node tests/e2e/run.js`, [E2E-HERMETIC.md](E2E-HERMETIC.md)) drives the binary over HTTP and the CLI through the served doors, the spend gate, the broadcaster ladder and the explorer rungs, so it judges all five floored files; it is a cargo test target, `tests/e2e_hermetic.rs`, gated by `E2E_HERMETIC_ORACLE=1` (unset, it passes at once, so the cargo shards and the PR gate never run it). The night runs two passes, and a mutant caught by either is caught: the union is the complete oracle's verdict.

1. **The cargo pass**: the fifty shards above.
2. **The survivors**: once all fifty succeeded, the job `Mutants survivors` collects every outcome that is missed or timeout (never caught, never unviable) by name, once (`.github/nightly/mutants_hermetic.py survivors`; a file the binary and the library both declare lists a mutant twice under one name, and the name selects both copies), into the artifact `cargo-survivors` (`survivors.txt`).
3. **The hermetic pass**: `Mutants-hermetic`, `MUTANTS_HERMETIC_SHARDS` shards (six) dealt round-robin over the survivors' names, starting after the cargo matrix ends (so its six run inside #144's six with nothing else running). Each shard reuses the `e2e-hermetic` job's setup (Node 24, `npm ci` in `tests/e2e`, Playwright's Chromium with `--with-deps`, `E2E_WALLET_TMP` on the runner), builds the MCP binary once (the mcp package is not mutated), runs the unmutated suite once as a stability check and refuses the shard if it fails (a flaky scene would read as a caught mutant), then runs cargo-mutants on the five files with one anchored, escaped `-F` per survivor, after checking that `--list` under that selection is the shard's survivors name for name, over `cargo test --locked --test e2e_hermetic` with `--baseline run --timeout-multiplier 2 --jobs 1` (cargo-mutants' baseline is the second unmutated run). The copy cargo-mutants builds in leaves the gitignored `node_modules` and browsers behind, so the step names the checkout's by `NODE_PATH` and `PLAYWRIGHT_BROWSERS_PATH`. A fault of the environment the test meets (a held port, a binary that is not this build's, no MCP binary) prints `E2E_HERMETIC_UNJUDGED`; cargo-mutants would read it as a caught mutant, so a log carrying the word refuses the shard. A shard writes its success marker as the cargo shards do, and uploads `hermetic-mutants-<shard>` (outcomes, logs, diffs, its names).
4. **The score**: the score job judges the night only when every cargo and every hermetic shard succeeded with its marker; `mutants_score.py --hermetic` counts a survivor the hermetic pass caught as caught (the column `by e2e_hermetic` says how many) and fails when a survivor has no hermetic outcome. The summary names the targets each pass ran under: the cargo selection, and `--test e2e_hermetic` in the hermetic configuration (`serve` without a tracker pass, the classic ARC stub, the explorers walled); the record carries the figure with those targets. `MUTANTS_FLOORS` is not moved by the pass's arrival: the floors are re-set from the complete oracle once a full night of it is scored.

**The hermetic pass's cargo-mutants.** cargo-mutants 27.1.0 adds every struct-field deletion mutant to any `-F` selection and ignores `-E` for them (upstream #632: its struct visitor never asks the name filters), so a shard of five survivors would also run all eighteen `delete field` mutants of the five files. Upstream fixed it in #634 (commit `b00aff0c6`, after 27.1.0, unreleased), and the hermetic shards install cargo-mutants from that commit (`CARGO_MUTANTS_HERMETIC_REV`); its `--list` of the five files at `6bf9a2c` is 27.1.0's, 1,191 names in the same order, and each shard's list check would refuse a name the two disagree on. The cargo pass stays on 27.1.0 (its selection is by file, which the bug does not touch); both move to the release that carries the fix. The same bug means an `exclude_re` line in `.cargo/mutants.toml` cannot skip a struct-field mutant under 27.1.0.

A surviving mutant is a place a lane could change the code and no test would notice. On a hot path it becomes an issue (or a line on the file's raise-the-floor issue): the mutant's name and diff from the artifact, and the test that would kill it. The fix is a test, never an exclusion; a mutant that is equivalent (no behaviour can tell it apart) is named in the issue with the reason, and only then skipped by an `exclude_re` line in `.cargo/mutants.toml` that names that issue.
