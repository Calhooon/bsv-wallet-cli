# The wallet-gate vectors (#130)

The stack's `conformance/wallet-gate-vectors.json` (bsv-stack-lean #184, its page `docs/p0/wallet-gate-vectors.md`) is the spend guard of `lean/Wallet.lean` as data: for each witness trace of the wallet, each step of it, each coin and each value of the action's word at the door (`allow_received`), the inputs the Lean evaluator saw and the answers it gave. Every row is `[M]`, computed by the evaluator and never edited by hand. The CLI replays all 490 rows against its own gate in the `vectors` job, so the gate is checked against the definition's rows on every PR, not against a reading of the charter.

## How a row is replayed

Each row gets a fresh in-memory store, written in the store's own records, and the toolbox's mock header service:

- **the creator**: its action (`is_outgoing` for `made`, `completed` when `mined`, else `unproven`) and its evidence as the host keeps it. `mined` is the toolbox's `proven_txs` path, `built` a tracker row, `announced` and `seen` the hints `heard` stores, `stale` the stored path with the stored reorg that took its block, the suspect mark a stored fork, `rejected` and `conflicted` a stored verdict, `unknown` no record but the action. A row whose creator's lineage is dead (`dead_lineage` true) names no ancestor, so the replay builds the scenario's (`2026-10-22-wallet-void-parent-descendants-stay-spendable`): a parent P of ours, `conflicted` by a mined competitor R (the tracker's stored word and verdict), whose change the creator spent (`spent_by` the creator's row). The mirror's parent is a received coin's creator; the walk reads a parent's word whatever its origin. The walk is the user's (#221): its candidates, its steps through `spent_by` and its heirs are the authenticated user's actions and outputs, as the Lean's lineage is one wallet's actions (`State.skel`); each row's creator and parent are one user's, so the rows read as before. No row plants a dead word beside a proof (P holds none), so the gate's reading of such a candidate with an eligible heir (in its own `read_creators` reading of the creators, the call's one header read, retried with them; a proof that checks reads mined for both) is driven by `spend_gate::tests::lineage`, not by the vectors.
- **the coin**: its satoshis, and its lock: `locked` is `spent_by` a live action of ours, `spent` is `spent_by` a completed one, `lost` is the relinquished record (`spendable = 0`, `spent_by` empty, as `reconcile-outputs` writes it), and an absent coin is no output.
- **the headers**: the tip at `headers_tip`, and at the creator's proof height a header carrying `header_root_at_proof_height` (the proof's own root when the row's names agree).
- **the host and the action**: `spend_depth`; `SPEND_OWN_CHANGE` on when the row names a rule for made change; the action's word off, `received`, and for a row with the word, the scoped word naming the row's coin (#63) as well.

Then the gate is asked through its public functions:

| function | compared against |
|---|---|
| `tracker_host::read_creators` | the creator's word must be the row's (a difference means the replay built the store wrong, and the test fails as a construction error); `creator_suspect`, read after the guard's own recheck |
| `spend_gate::lineage_candidates`, `Lineage::dead` | `dead_lineage`: the creator's lineage as the gate's walk reads it (the user's walk, #221), a candidate holding a proof with an eligible heir read through `read_creators` as the gate reads it (#163) |
| `spend_gate::hold_reason` on that reading | `door_spendable`; `guard_depth` where the reason names the depth |
| `spend_gate::assess_named` (a named input) | `offerable`, `offerable_clause` |
| `spend_gate::assess` (the allocation's offer) | `offerable`; `offerable_clause` when the coin is offered or held with a reason |

`door_spendable` is projected from a copy of the reading with the mark set aside (`suspect` false, `offered` the reading's `door`, the guard's own door at its depth), because `Wallet.doorSpendable` reads no mark (`offerableUnder` checks `!a.tracker.suspect` apart from the door) while the gate's hold word says the mark first; the mark itself is compared as `creator_suspect`. The gate holds on the mark for every word, after a fault and before the door (`spend_gate::hold_reason`, one site, #211), as `offerableUnder` refuses it whatever the word; no reading the crate produces today carries it on a word other than `mined`.

A hold's reason maps to the Lean's clause: `frozen` to frozen; `spent by`, `lost:` (the store's `spendable = 0` with no spender on a `completed` or `unproven` transaction, #165, #197), and `its transaction is <status>: not spendable until it is sent` (#219, an unspendable named record) to held by a lock; `suspect:` to creator suspect; `<word>: never offered` and `its transaction is failed: never offered` to a chain word against the creator; `received, no proof`, `received, confirming again` (a held `stale` creator, #162) and `SPEND_OWN_CHANGE=0` to no rule for the creator's origin; a bare `depth N:` to mined shallower than the guard's depth; and `dead lineage:` (the gate's lineage hold, #163) to dead lineage.

The columns the gate gives no value for are named by the test's `COLUMNS_NOT_ANSWERED` and printed on every run: `rule_for`, `received_pending`, `door_word`, `coin_word` (the gate computes none of them apart from its hold), and `host_answer` (a row names its door but carries none of its arguments, so the host's answer at that door cannot be replayed from the row).

The vectors do not simulate a header-service outage. When that service
cannot answer, the gate still holds the coin on `headers unavailable: ...`
and retries as before; the listed creator word is the stored tracker word,
not the tier an interrupted replay reached (#212). The spend-gate tests
cover stale creators in both store shapes, a stored mined creator, and a
toolbox proof without a tracker row, which reads `unknown`: the tracker
never held a word for it. Other check faults also preserve a known stored
word; a root mismatch remains the replay's reading. Wire fixture
`084-createAction.headersUnavailable.json` records the stored `mined` word
in the hold and its message. The vector bytes and divergence list do not
change.

### A word after the door

The named door offers our own change under `SPEND_OWN_CHANGE=1`, as the Lean's own-change rule does ([SRC] bsv-stack-lean `103c5bd`, `lean/Wallet.lean:3044`). Toolbox 0.14.0-beta.3 then refuses a named change coin in `createAction.inputs` as managed by the wallet ([SRC] `src/storage/sqlx/create_action/inputs.rs:142-146`), served as `400 VALIDATION_ERROR` with its message, `Validation error: The inputs[0] parameter must be an unmanaged input. Change outputs are managed by your wallet.`; [wire fixture 120](../tests/wire/120-createAction.namedChange.json) records it. The typed refusal's Display no longer adds `wallet error: ` (#330). The keeper's reading on [#234](https://github.com/Calhooon/bsv-wallet-cli/issues/234#issuecomment-6415020424) records this as a door constraint beside the Lean: the reference's `applyStoredInputScript` throws `WERR_INVALID_PARAMETER` on `inputs[vin]` when the stored output is change, requiring `an unmanaged input. Change outputs are managed by your wallet.` ([SRC] ts-stack `edf6e03`, `packages/wallet/wallet-toolbox/src/storage/methods/createAction.ts:966-978`); the toolbox states the same rule in its own words. The rules sit on different axes: the Lean's is the guard's word on offerability, the reference's the door's word on who may name an input, with managed change the wallet's to allocate. CLI `--from` (#313) uses the toolbox's must-spend list beside the offer, after the same gate judges every named coin; it never sends managed coins through `createAction.inputs`. The vectors' `offerable` stays the guard's answer. `respend` never meets the toolbox's named-input check: its exact inputs pass `assess_named` with the phantom's reservation, and it builds and signs the replacement itself (`src/respend.rs:198-232,316-375`).

## The unexpressed rows

`UNEXPRESSED` in the test lists the rows whose state the CLI cannot hold, each with why. The list is exact: the test computes the class from the rows and fails when it differs from the list, so a row that becomes expressible (or a new row that is not) fails until the list is changed. At this pin, 486 rows are expressed and 4 are not:

- **the creator is `abandoned`** (2 rows, `WalletGate.contendedSteps` step 5, `T1.0`): the CLI's tracker row stores no abandon, so no store reads `abandoned`. An action the host gives up is the toolbox's `failed` status, which the allocation never reads as a candidate.
- **the creator is mined above the headers' tip** (2 rows, `Wallet.Check.depth_floor`): the CLI checks the stored proof against the headers on every read and the tracker refuses a proof above the tip, so the reading is `unknown`, never `mined`.

The named door's record/status hold (#219) does not change that set: all 4 rows stay unexpressed, including the 2 abandoned rows. A named failed input reads the host's `failed` status (the Lean's dead creator makes its free coin `void`); no tracker store reads `abandoned`, and expressing those rows is outside this change. The test `a_named_inputs_status_hold_maps_to_its_record_or_creator_clause` plants unspendable live records and a failed coin, then maps the held reasons returned by `assess_named`: live statuses map to the coin's own lock clause, failed to the creator's chain-word clause. It fails with either mapping removed, and when the status/flag hold is removed. The real-store tables `LEAN_SEGMENT_READINGS` and `SCOPED_WORD_DOMAIN_READINGS` separate the Lean's segment, where the doors agree, from the scoped word's domain, where they differ.

## The divergences

A difference between the gate and a row is a finding. It is never fixed by changing the gate in this test's commit, nor by changing a row. `wallet_gate_divergences.json` records each one. That list is exact too: a difference it does not hold fails the test, printed as a `DIVERGENCE` line ready to record, and so does an entry that no longer differs. When the gate is fixed, the fix's commit removes its entries. At this pin the list is empty, 0 differences over 0 rows and no finding: the test prints `gate vectors: 0 divergences, every one recorded: true` and no finding line, and a new difference still fails as a `DIVERGENCE` line, as an entry that no longer differs would. Five left with their fixes: `lost-coin-not-read` (24 rows, 138 differences, 22 rows on `offerable`: the gate did not read the relinquished record, #165); `named-absent-coin` (14 rows, 21 differences, all on `offerable`, #166): `assess_named` left an outpoint that is not a coin of this wallet to the toolbox's allocation to refuse, and the replay read that hand-off as offerable; the gate now refuses it itself, the caller's 400 (`GateError::Scope`, `not a coin of this wallet`, the scoped word's refusal), before a creator is read or anything is stored, and the replay reads that refusal as the Lean's `no coin`; and `fork-recheck-clears-suspect` (2 rows, 14 differences, both on `offerable`, #164): the spend guard fed the crate's `SpendAttempt` then `Recheck` on every spend, and under a fork in progress at the creator's height our header there still carries the stored root, so the recheck cleared the fork's suspect mark and the gate offered a coin the Lean holds; the guard now reads the mark and refuses the coin, feeding nothing, and only the tracker's own steps (a tip's or a resolved split's recheck, a reorg's recheck, a new proof) clear it. The latch rows' `door_spendable` is read with the mark set aside (above), as the Lean's door is; before #164 the guard cleared the mark, so the gate's whole hold and the Lean's door agreed by accident there. And `stale-door-reads-seen` (12 rows, 57 differences, 5 rows on `offerable`, #162): `hold_reason` read `stale` beside the dead words and held the coin `stale: never offered`, while `Wallet.doorWord` reads a `stale` creator as `seen` (the owner's ruling 7a of 2026-10-20); the gate now offers it under the rule a pending creator's coin is, our own change under `SPEND_OWN_CHANGE` and a received coin under the action's word, and holds it with no rule (`stale: its block left the chain; ...`), so the latch and orphaned rows' `T.0` and the reorged received row's `B.0` move on `offerable`, `offerable_clause` and `door_spendable`; `rejected`, `conflicted` and `abandoned` still close the door. And `no-lineage` (12 rows, 72 differences, all 12 on `offerable`, #163): the gate read a coin's creator alone, while `Wallet.deadLineage` holds a coin whose creator's lineage reaches a dead action of this wallet, made or received (the owner's lineage ruling of 2026-10-22), so `D.0` of the three `Wallet.Check.lvDead` traces (steps 9 and 10) and `U.0` of the mirror (step 4) were offered under the `made` rule; the gate now walks the store's `spent_by` edges from the dead actions (`lineage_candidates`, one read of the store; a candidate holding a proof is read only when it has an eligible heir, with the gate's creators in the call's one header read, never apart, and each door, the allocation's and the named input's, re-reads once what faulted (`read_batch`); `Lineage::dead` derives the dead set after; #217 bounds proof selection by all eligible creators, including later lazy batches, or the eligible named creators) and holds such a coin `dead lineage: ancestor <txid> <word>` after the door, so those rows move on `offerable` and `offerable_clause` on all four doors, and the `dead_lineage` column is now answered on every expressed row.

## Moving the pin

The 0.18.2 probe move (#196) and internalize-only instruction bound (#157) change no gate-vector row or divergence: the probe asks the toolbox's explorer ladder, while the bound validates the request before storage. [Wire fixture 123](../tests/wire/123-internalizeAction.customInstructionsBound.json) records the bound's 400 refusal; neither changes the gate's offerability decision.

1. Copy the file at the stack's new commit: `git -C ~/bsv/bsv-stack-lean show <commit>:conformance/wallet-gate-vectors.json > tests/vectors/wallet_gate_vectors.json`.
2. Write the commit and `shasum -a 256 tests/vectors/wallet_gate_vectors.json` into the pin, and the sha256 into `vectors_sha256` of the divergences file.
3. Run `cargo test --locked --test gate_vectors -- --nocapture`. A new row the CLI cannot hold fails the unexpressed list; a new difference prints its `DIVERGENCE` line. Record each under a finding (a new finding gets its description in the file), and update the counts on this page.
4. Commit the copy, the pin and the lists together, the stack's commit named in the message.

`underReceivedRule` label beside the host label. Signed noSend outputs now
have flag 1; the named gate holds them by status with the same nosend reason.
The Lean segment and vector bytes are unchanged. Abort fixture 124 records
the toolbox's accepting-status refusal, while the host's proof guard retains
