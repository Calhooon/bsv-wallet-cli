- **The inspector's origins view (#414, #440).** `bsv-wallet ui` shows the store's per-origin rows at `/origins`: each open pending request (originator with its port, scope, call, amount, seen at, renewal) with Grant, Grant once (a spending request) and Deny, and each grant row with Revoke. Its routes are `GET /api/origins`, `POST /api/origins/answer` and `POST /api/origins/revoke`, in the owner's door's bodies and the JSON `bsv-wallet origins --json` prints, written through the `origin_grants` module; of two places answering one row the loser is told (409). The two write routes admit only the inspector's own `Origin` (`http://` and the `Host` it was asked by), never an origin `ALLOWED_ORIGINS` lists or a grant admits: a granted page must not write a grant. Every read of the inspector, `/api/query`'s among them, is on a pool opened read-only (`SQLITE_OPEN_READONLY`), so the database refuses any write whatever the SQL's text: a `;` and a second statement, a CTE before an `INSERT`, a `PRAGMA` that writes; before, a statement-prefix check on a read-write pool was the only guard and a `SELECT 1; INSERT ...` wrote. The prefix check stays as a courtesy message and now admits `WITH`. A missing wallet file is refused by name, never created.
