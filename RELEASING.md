# Releasing bsv-wallet-cli

1. Every change reaches `main` through a pull request; `main` is protected, admins included, linear history. `main` is the stable line: patches (fixes, pin moves, docs) land here, and another lane, Zanaadu, LOW or the stack takes a quick fix from it.
1a. The north-star programme (the epic, issue 106) lands on `beta`, protected with the same rules. `main` merges into `beta` after every stable patch; `beta` merges into `main` at a phase exit as the next minor, after the mainnet gate and a day of canary on a prerelease tag. A `vX.Y.Z-beta.N` tag is cut from `beta` and publishes a crates.io prerelease (a consumer takes one only by naming it); it is never moved to `main`. The minor is tagged fresh on `main` after the merge.
1b. A beta prerelease is announced to each captain in `docs/DEPENDENTS.md` before any consumer takes it. The announcement names the tag and carries the consumers' fixtures' diff since the last minor: `git diff vX.Y.0 vX.Y.Z-beta.N -- tests/wire_consumers`, cut per consumer directory, so each captain reads only the calls their code sends and what changed in the answers. A consumer with no changed fixture gets a line saying so. The canary order holds: the stack's witness wallet and LOW's fleet stay on the previous version until the release has soaked a day; the other consumers follow on their captains' word. The keeper's versions page records the tag each consumer runs once it moves, and `docs/DEPENDENTS.md`'s version column is brought to it in the same PR as the next fixture change.
2. The PR merges (rebase-merge) once its required checks are green: on `main` `Test`, `lint` (Rustfmt, locks, deny, Clippy and the ratchet, each its own named step, #471), `vectors` and `Build (ubuntu-latest)`; on `beta` those and `wire` and `e2e-hermetic`.
3. A release is a PR like any other: bump `version` in `Cargo.toml` (and `Cargo.lock` with it), run `python3 tools/changelog --assemble X.Y.Z`, and commit `CHANGELOG.md` and the emptied `changelog.d/` (keeping its `README.md`) beside the version bump; merge it green. Assembly carries the existing Unreleased body verbatim ahead of the fragments and leaves Unreleased empty. A beta prerelease from `beta` assembles the same way under its own version string, `python3 tools/changelog --assemble X.Y.Z-beta.N`, before its tag is cut. For a minor cut after a prerelease that carried everything, with no new pending changes, use `python3 tools/changelog --assemble X.Y.Z --allow-empty`; it records `No changes since ...` using the following release heading from the file.
4. Before a minor tag (never for a prerelease), dispatch the measurements on the line and read them green: `gh workflow run bench.yml --ref <line>`, `gh workflow run differential.yml --ref <line>`, `gh workflow run nightly.yml --ref <line> -f mode=complete` (the mutation score over every floored file and the fuzz hours), `gh workflow run build-macos.yml --ref <line>`; a push and a pull request run exactly the required set (the owner's word of 2026-10-27). Then tag the merged commit on `main`: `git tag vX.Y.Z <sha> && git push origin vX.Y.Z` (the tag must equal `Cargo.toml`'s version).
4a. At each pin of a prerelease, the complete Nightly at the fleet's 17:30Z slot (the keeper's line of 10:0xZ on 2026-11-03 on the runner pool's read: the lightest hours, 16Z to 18Z, beside the toolbox's 16:00Z; docs/NIGHTLY.md, #456, #514): `gh workflow run nightly.yml --ref beta -f mode=complete` on the pinned commit, twenty Mutants shards, fourteen at a time then six (the account's concurrent-job limit, less a PR run's six runners, #496; a shard past the job's limit refuses the night with the shard named, and the count does not grow; docs/NIGHTLY.md, #460), its record (the artifact `night-record`) committed over `docs/scoreboard/mutants.json` as the new last complete run. It is the only night that may move a floor; the incremental nights between pins mutate the floored files changed since it and carry the rest with its run and sha (docs/NIGHTLY.md, the two modes, #462).
5. The tag runs `.github/workflows/release.yml`: it checks the tag against the manifest and that the commit is on `main`, re-runs the CI jobs, then `cargo publish --dry-run` and `cargo publish`, and beside them builds the binaries and creates the GitHub release.
6. Nothing publishes from a laptop; no crates.io token is stored anywhere, in this repository or its secrets.
7. Publishing uses crates.io trusted publishing: the crate's Trusted Publishing setting names owner `Calhooon`, repository `bsv-wallet-cli`, workflow `release.yml`, no environment.
8. A failed release job publishes nothing; fix through a PR, then the owner moves the tag to the fixed commit, or tags the next patch.
9. A published version is never re-published; a bad release is yanked on crates.io and superseded by the next patch.
10. Without the trusted-publishing setting on crates.io the publish step fails closed; the binaries still build.
