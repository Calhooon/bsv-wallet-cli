# Releasing bsv-wallet-cli

1. Every change is born on `beta` (the owner's ruling of 2026-11-18; the stack's record `docs/DECISIONS-2026-10-19.md`, section 31.1). A change reaches `beta` through a pull request and beta's merge queue (`docs/lanes/README.md`, rule 14); `beta` is protected, admins included, linear history. Nothing is born on `main`.
1a. `main` is the stable line: protected, admins included, linear history. It takes a stable roll-up and nothing else (the direction rule below, points 11 to 15), and `beta` merges into it once, at the cut, on the owner's tag (point 18). Another lane, Zanaadu, LOW or the stack takes a quick fix from a roll-up's release. A `vX.Y.Z-beta.N` tag is cut from `beta`'s tip and publishes a crates.io prerelease (a consumer takes one only by naming it); it is never moved to `main`.
1b. A beta prerelease is announced to each captain in `docs/DEPENDENTS.md` before any consumer takes it. The announcement names the tag and carries the consumers' fixtures' diff since the last minor: `git diff vX.Y.0 vX.Y.Z-beta.N -- tests/wire_consumers`, cut per consumer directory, so each captain reads only the calls their code sends and what changed in the answers. A consumer with no changed fixture gets a line saying so. The canary order holds: the stack's witness wallet and LOW's fleet stay on the previous version until the release has soaked a day; the other consumers follow on their captains' word. The keeper's versions page records the tag each consumer runs once it moves, and `docs/DEPENDENTS.md`'s version column is brought to it in the same PR as the next fixture change.
2. A pull request into `beta` lands through the merge queue (a rebase) once its required checks are green: `Build (ubuntu-latest)`, `Test`, `vectors`, `wire`, `e2e-hermetic`, `lint` and `main-in-beta`. A pull request into `main` lands by rebase merge, never by squash (a squash drops each pick's `(cherry picked from commit <sha>)` line), once its required checks are green on a branch up to date with `main`: `Build (ubuntu-latest)`, `Test`, `vectors`, `Rustfmt`, `Clippy`, `deny`, `locks` and `beta-born` (each line's protection as read on 2026-11-27, with the direction rule's check).
3. A prerelease is cut from `beta`'s tip, by a pull request into `beta` like any other: bump `version` in `Cargo.toml` to `X.Y.Z-beta.N` (and `Cargo.lock` with it), run `python3 tools/changelog --assemble X.Y.Z-beta.N`, and commit `CHANGELOG.md` and the emptied `changelog.d/` (keeping its `README.md`) beside the version bump; land it green and tag the landed commit on `beta`. Assembly carries the existing Unreleased body verbatim ahead of the fragments and leaves Unreleased empty. A prerelease carries everything `beta`'s tip holds: nothing on `beta` is reverted and landed again so that a prerelease carries a pin alone. A stable version is made by a roll-up (point 13) or by the cut (point 18), never by a pull request into `main` that is born there.
4. Before the cut's tag (never for a prerelease or a roll-up), dispatch the measurements on `beta` and read them green: `gh workflow run bench.yml --ref beta`, `gh workflow run differential.yml --ref beta`, `gh workflow run nightly.yml --ref beta -f mode=complete` (the mutation score over every floored file and the fuzz hours), `gh workflow run build-macos.yml --ref beta`; a push and a pull request run exactly the required set (the owner's word of 2026-10-27). A tag must equal `Cargo.toml`'s version: `git tag vX.Y.Z <sha> && git push origin vX.Y.Z`, on the owner's word.
4a. At each pin of a prerelease, the complete Nightly at the fleet's 17:00Z slot (the keeper's slot table of 11:0xZ on 2026-11-03, from 2026-11-04: the light window 17:00Z to 18:00Z, hour 16 the day's highest non-heavy p95, and the toolbox's 18:00Z slot opening after this repository's hour ends; docs/NIGHTLY.md, #456, #514, #522): `gh workflow run nightly.yml --ref beta -f mode=complete` on the pinned commit, twenty Mutants shards, six at a time in four waves (the fleet's cap on every heavy run while the account's runner pool reads busy, until an occupancy read shows the non-heavy p95 under 10, #513; a shard past the job's limit refuses the night with the shard named, and the count does not grow; docs/NIGHTLY.md, #460), its record (the artifact `night-record`) committed over `docs/scoreboard/mutants.json` as the new last complete run. It is the only night that may move a floor; the incremental nights between pins mutate the floored files changed since it and carry the rest with its run and sha (docs/NIGHTLY.md, the two modes, #462).
5. The tag runs `.github/workflows/release.yml`: it checks the tag against the manifest and that the commit is on its line (a plain `vX.Y.Z` on `main`, a `vX.Y.Z-beta.N` on `beta`), re-runs the CI jobs, then `cargo publish --dry-run` and `cargo publish`, and beside them builds the binaries and creates the GitHub release.
5a. The advisories are read apart from a pull request (the owner's ruling of 2026-11-17, #596): the `deny` step of `lint` reads bans, licenses and sources in the merge queue and on a pull request whose diff changes a path it reads (#473), and `.github/workflows/advisories.yml`, scheduled from `main`, reads the RustSec advisories once a day for `main` and `beta` and keeps one issue per line titled `advisories: <line>`, opened or rewritten on a finding and closed by a clean run. A tag's run reads all four cargo-deny checks (advisories, bans, licenses, sources; the `deny` step of `lint`), and an open `advisories: <line>` issue is settled before a tag by a lock move, a dependency change or an entry in the stack's template, never by an ignore written here alone.
6. Nothing publishes from a laptop; no crates.io token is stored anywhere, in this repository or its secrets.
7. Publishing uses crates.io trusted publishing: the crate's Trusted Publishing setting names owner `Calhooon`, repository `bsv-wallet-cli`, workflow `release.yml`, no environment.
8. A failed release job publishes nothing; fix through a PR, then the owner moves the tag to the fixed commit, or tags the next patch.
9. A published version is never re-published; a bad release is yanked on crates.io and superseded by the next patch.
10. Without the trusted-publishing setting on crates.io the publish step fails closed; the binaries still build.

## The direction rule (the owner's ruling of 2026-11-18)

Every change is born on `beta`. `main` takes only a quick fix of six classes, the six of bsv-rs's `RELEASING.md`, "The direction rule" (the fifth and the sixth by the owner's word of 2026-11-12):

- a security advisory (of this crate, or of a crate it pins);
- a panic on input;
- a wrong verdict: a wrong consensus or BEEF verdict, or a coin credited, offered or spent wrongly;
- a break in a live dependent (`docs/DEPENDENTS.md`);
- the front pages (the fifth class; the owner's word of 2026-11-12): here `README.md`, the page crates.io and GitHub show for the stable line (this repository has no `SECURITY.md` and no folder of release notes; `release.yml` has GitHub generate a Release page's notes). `main` takes each such commit of `beta` by `git cherry-pick -x`, resolved to what `main`'s tree proves: a sentence whose matter `main` lacks is cut from `main`'s README, and a section of `beta`'s alone stays `beta`'s;
- a toolchain mend (the sixth class; the owner's word of 2026-11-12): a mend that a required check on `main` demands after a release of CI's toolchain, with no behaviour change, taken by `git cherry-pick -x` of the `beta` commit that mended the same line.

11. Every commit of `main` is a `git cherry-pick -x` of a `beta` commit with its test. The `-x` line, `(cherry picked from commit <sha>)`, is the link both checks read; a pick resolved by hand keeps it, and one made without it fails the checks until `git commit --amend` adds it. The pull request into `main` says its class in one line of its body: `Class: security advisory`, `Class: panic on input`, `Class: wrong verdict`, `Class: break in a live dependent`, `Class: front pages` or `Class: toolchain mend`.
12. Two shapes of commit are born on `main` by nature, because no `beta` commit can hold them, and the checks let each through and say so in the log. A hop commit: the stable pins and the lock, that is `Cargo.toml` lines of the `bsv-*` crates and `Cargo.lock`, nothing else (the lock alone is a hop commit too). A version commit: `Cargo.toml`'s `version`, `Cargo.lock`'s line for it, the new section of `CHANGELOG.md`, and the `changelog.d/` fragments the section assembled, deleted; nothing else. No test, no source and no other document rides in either.
13. A stable roll-up. Quick fixes travel together, and this crate hops once per roll-up of a crate it pins: one release per line per roll-up, never a release for each fix of a crate below. In order: (a) each fix lands on `beta` through the queue, with its test and its fragment; (b) on a branch from `origin/main`, `git cherry-pick -x <beta sha>` for each, in beta's order, each pick's test run; (c) if the roll-up moves a pin, one hop commit per crate: the `=X.Y.Z` requirement and `cargo update -p <crate> --precise X.Y.Z`; (d) the version commit: `version` in `Cargo.toml` and `Cargo.lock`, and the section of `CHANGELOG.md`, assembled from the fragments the picks brought (`mkdir -p tools && git show origin/beta:tools/changelog > tools/changelog && python3 -B tools/changelog --assemble X.Y.Z && rm tools/changelog && rmdir tools`; with no fragment, as in a roll-up that is a hop alone, the heading `## [X.Y.Z] - YYYY-MM-DD` and its section are written by hand under `## [Unreleased]`); a hop's sentences are written into the section by hand; (e) the pull request into `main`, its body carrying the class line and each pick's `beta` sha, green on main's required checks, `beta-born` among them, landed by rebase merge; (f) the mainnet gate, once, on the landed commit (`docs/lanes/README.md`, rule 3); (g) the tag `vX.Y.Z` on the landed version commit, on the owner's word (rule 5); (h) the link on `beta` (point 14), in the same sitting.
14. The link. A version commit has no source on `beta`, so `main-in-beta` holds `beta` until a commit of `beta` carries its `(cherry picked from commit <sha>)` line. That commit is one docs-only pull request into `beta`: `CHANGELOG.md` gains the released section as `main` words it, above the previous stable section; `beta` keeps its own `version`, its own Unreleased and its own fragments. Its subject: `link: X.Y.Z into beta: the version commit linked; the released section added above <previous>'s`. An empty commit is not a link: the queue's rebase drops it. From the roll-up's landing on `main` to the link's landing, nothing else is added to beta's queue.
15. The fix reaches `beta`'s users by the next prerelease, cut from `beta`'s tip (rule 3). When a published advisory names the fix, the prerelease that carries it is cut in the roll-up's sitting.
16. The checks (`.github/workflows/lines.yml`, `.github/ci/lines.sh`; `.github/ci/test_lines.py` is their proof). A commit is on a line by sha, by patch (`git cherry`), or by a cherry-pick line in either direction: the commit names a source the line holds, or a commit of the line names it. `beta-born`, on every pull request into `main`, asks that of each commit of the pull request against `origin/beta`, and lets a hop commit and a version commit through. `main-in-beta`, on every pull request into `beta`, every merge-queue group and every push to `beta`, asks it of each commit of `origin/main` after the baseline (`MAIN_BASELINE` in `lines.yml`: `9358665d`, main's tip of 2026-11-27, the last commit born under the old direction), and lets a hop commit through. Each fails naming the commits that are none of these. The three files are the same bytes on both lines.
17. What `main` carried on 2026-11-27 that `beta` did not goes to `beta` once, by one pull request into `beta` (HANDOFF.md whole and `.github/workflows/advisories.yml`; the stable patches through 0.18.9 were ported before the rule). After that nothing is ported from `main`.
18. The cut. `beta` merges into `main` once per minor, on the owner's tag, behind the bar: the milestone's rows closed and rule 4's measurements read green. In order: (a) the last pull request into `beta` is the version commit `X.Y.0` (rule 3's assembly under the stable version); (b) `main-in-beta` is green on `beta`'s tip and `beta`'s `CHANGELOG.md` holds every `## [...]` heading `main`'s holds; (c) a branch `cut/X.Y.0` from `origin/beta` takes `git merge -s ours origin/main`, so its tree is `beta`'s tree and its history holds both lines; (d) its pull request into `main` is the one pull request that lands as a merge commit, by the owner's hand (the linear-history requirement on `main` lifted for that merge and restored after it; the required contexts of `main` brought to those `beta`'s `ci.yml` reports before it); (e) the tag `vX.Y.0` on that merge commit; (f) on `beta`, the next pull request sets the next prerelease version and moves `MAIN_BASELINE` to the cut's merge commit.
19. HANDOFF.md, the captain's record, lives on `beta` and lands there as a docs-only pull request through the queue (`docs/lanes/README.md`, rule 16). `main`'s copy stopped at the entry of 2026-11-18 and is replaced by `beta`'s at the cut. A captain's start reads `git show origin/beta:HANDOFF.md`; the standing checkout sits on `beta`.
20. On a day the queue cannot land a fix that a published advisory or a live break needs: a roll-up that is a hop and a version commit alone needs nothing from `beta`. For a code fix, the owner alone may take `beta-born` out of `main`'s required contexts for that one pull request and put it back in the same sitting; the fix then lands on `beta` as soon as the queue runs, carrying the main commit's `(cherry picked from commit <sha>)` line, and `main-in-beta` holds `beta` until it does. The record of the day names the hour of each of the two writes.
21. The default branch's copy of a workflow (ruled by the owner's word of 2026-11-28; the stack's `docs/RULINGS-2026-10-12.md`, under that date: it is a road to `main` beside the six classes, it was his to give, and it carries workflow files alone). GitHub runs a dispatched or a scheduled workflow from the default branch's file, so `main` carries a copy of `.github/workflows/nightly.yml`, `.github/workflows/cache-beta.yml` and `.github/workflows/advisories.yml`. A change to one of them is born on `beta`; `main`'s copy takes it by `git cherry-pick -x` of that `beta` commit, in a pull request whose commits touch workflow files and nothing else and whose body says `Class: none; the default branch's copy of a workflow`. The three files are named here; a fourth is added by a pull request into `beta` that changes this point (bsv-rs's own rule takes its three such files the same way).
