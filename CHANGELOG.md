### Changed

- **The pins:** `bsv-rs` `=0.8.14` and `bsv-wallet-toolbox-rs` `=0.13.9`. 0.13.8 is "a security patch on the stable line, and nothing else" (its `bsv-rs` floor). Every test of 0.18.9 answers the same on 0.13.9.

#### What the toolbox's 0.13.9 changes for this CLI

This CLI is "a wallet over one local store with no manager"; in the toolbox's words, it "meets the change selection, the send of a `noSend` action, the `sendWith` rule, `abortAction` of a `noSend` action, the store's `find_or_insert_user`, the temp folder and the new index", and, on `daemon`, the status review's, the proof task's and the unfail task's entries, where a monitor runs.

- **The change selection** "takes only a coin the store holds as spendable", whether or not the action accepts delayed broadcast.
- **A `noSend` action:** its "change and basket outputs become spendable when it is sent". `abortAction` of a `noSend` action "writes its request `invalid` beside the `failed` row", and on `daemon` the unfail task asks the network of it: "each pass (every 10 minutes by default) asks at most 20 such actions", each "at most once an hour until it has been asked 24 times, then at most once a day".
- **`sendWith`:** "a txid named in `sendWith` is sent only when it is the caller's own `noSend` transaction"; one aborted is "answered `failed` in `sendWithResults` and never posted". The served `/createAction` passes no `sendWith` through (below, Known).
- **The temp folder:** "no BEEF hex file is written to the host's temp folder". An operator "may delete the `beef-*.hex` and `beef-rejected-*.hex` files an earlier release left in its temp folder; nothing reads them".
- **The new index, at the open after the upgrade:** the open (`make_available()`, as every command of this CLI opens its store, or `migrate()`, as `init` runs it) builds `idx_transactions_updated_at` "in one pass that reads every row of `transactions` once, on the store's writer, so the store's other writes wait for it"; `migrate()` answers `007_transactions_updated_at`. A store on a read-only file cannot build it: open it writable once after the upgrade. Run on a test store made by 0.18.9's toolbox, 100,000 transaction rows, 473 MB: the open built it in 242.4 ms (a later open took 3.9 ms); `migrate()` on an untouched copy took 542.7 ms. **The way back:** 0.18.9's toolbox opened that store afterwards with no refusal (`make_available()` answered Ok, `migrate()` answered `005_proof_root_checks`), the index left in place and the rows whole (`PRAGMA integrity_check`: `ok`), and this release opened it again after. An operator who rolls back to 0.18.9 can open the upgraded store.

### Known

- **A payer on the reference's SDK from 4.1 cannot complete a paid HTTP request through this line.** In the toolbox's words, its "submitting call (`createAction` with `sendWith` and no inputs or outputs) is answered as a new action". This host does not read `sendWith` on the served `/createAction` (#147).

## [0.18.9] - 2026-11-18

A security patch and the toolbox's script check on the stable line: `bsv-rs` `=0.8.12` to `=0.8.13` and `bsv-wallet-toolbox-rs` `=0.13.5` to `=0.13.7`. `bsv-tracker` `=0.8.0` is unchanged (the toolbox's requirement of `bsv-rs` is unchanged at `0.8.12`, which 0.8.13 meets), and so is the tracker's pass: its record of an accepted claim is as in 0.18.8 (#620). `Cargo.toml` moves the two requirements and this crate's version; `Cargo.lock` moves three rows, `bsv-rs` (0.8.12 to 0.8.13) and the toolbox's (0.13.5 to 0.13.7), each its version and checksum, and this crate's own (0.18.8 to 0.18.9); no row is added or leaves; `mcp/Cargo.toml` is unchanged. The code that moves: `src/genesis.rs` (new: the Genesis height the toolbox's door judges by, per chain, and a check of a BEEF by that rule alone), `src/spend_gate.rs` and `src/commands/split.rs` (`split`'s hold), `src/commands/gift_chain.rs` and `src/commands/gift_claim.rs` (`gift-claim`'s check before its post). Upgrade by installing 0.18.9: `cargo install bsv-wallet-cli --version 0.18.9 --locked`.

- **bsv-rs 0.8.13: [GHSA-j4w5-4g84-q3f4](https://github.com/Calhooon/bsv-rs/security/advisories/GHSA-j4w5-4g84-q3f4) (medium).** The advisory's summary: "GlobalKVStore selector queries (get_by_controller, get_by_tags, query) do not enforce the selector against the overlay resolver's answer, so an untrusted lookup host can return a validly-signed token of another controller or tags for a selector query." Every release from 0.3.1 through 0.8.12 is affected; 0.8.13 is patched. This CLI compiles bsv-rs's key-value store in (its `full` feature) and calls none of its doors: no `GlobalKVStore` or other key-value store use in `src/`, `mcp/src/` or `tests/`, nor in the sources of bsv-wallet-toolbox-rs 0.13.7 or bsv-tracker 0.8.0 (read in the sources, not from a run).
- **bsv-wallet-toolbox-rs 0.13.7: `internalizeAction` runs a received transaction's scripts** (0.13.6 is "a security patch on the stable line, and nothing else": its `bsv-rs` requirement moves to 0.8.12). What changes, in its words: "`internalizeAction` runs the unlocking script of every input of every transaction of a received AtomicBEEF that the BEEF does not prove (the subject and each unproven ancestor) against the output it spends, and refuses the request, with nothing written, when one does not pass: `wallet error: Validation error: spend refused at offset <n>, input <i> of <txid>: <why>`." "A repeated `internalizeAction` of a transaction the store already holds is checked the same way." What a host does: "A host that receives ordinary payments (standard spends such as P2PKH, of coins mined after Genesis or carried unmined in the BEEF) sees no answer change"; "A received payment that passes these checks is answered and counted as in 0.13.6."
- **What now answers differently**, door by door. `POST /internalizeAction` (read from runs through this CLI's router, `tests/served_internalize_scripts.rs`): a payment whose unproven subject, or whose unproven ancestor, has an input that does not pass is refused, 400 `VALIDATION_ERROR`, `wallet error: Validation error: spend refused at offset <n>, input 0 of <txid>: OP_EQUALVERIFY requires the top two stack items to be equal.` (`<txid>` the subject's or the ancestor's); a payment spending a coin its BEEF proves at height 600,000 is refused, 400 `VALIDATION_ERROR`, `... input 0 not judged: coin height 600000 is before Genesis height 620538.`; a transaction the store holds, handed again unproven with an input that does not pass, is refused the same way, where the proven repeat is answered as before. Each was admitted through 0.18.8; each refusal writes nothing, posts nothing and leaves the balance unmoved, and the same payment made well is stored. `fund`, `receive` and `sync` print the door's refusal whole and write nothing (read in the code): `fund` returns it as its error (`src/commands/fund.rs:58-61`), `receive` as `refused tx <txid> from <courier>: wallet error: Validation error: ...` (`src/commands/receive.rs:71-73`, the path `l2_stub_refusal_names_txid_courier_reason_and_stores_nothing` drives), `sync` as `failed <txid>.<vout>: refused tx ...`, counted refused (`src/commands/sync.rs:173-185`). `split` and `gift-claim`: below.
- **What is refused that a node might still mine** (the toolbox's words): "A payment spending a coin mined before the network's Genesis height is refused as not judged even when the BEEF proves that coin: `input <i> not judged: coin height <h> is before Genesis height 620538.` on mainnet"; and "a spend that consensus allows and the standard word does not is refused when it sits in the subject or in an unproven ancestor". The served door answers 400 `VALIDATION_ERROR` with that text; `fund`, `receive` and `sync` print it. `split` posts and then records its outputs through that door, so it does not spend a coin whose spend the door would refuse so: a coin whose creator the wallet's own records prove below the chain's Genesis height, or the unmined change of a spend of one. Such a coin is held for `split` alone, its reason `mined before Genesis: coin height <h> is before Genesis height 620538; split does not offer it` (or `mined before Genesis: <txid> is not mined yet and spends a coin of height <h>, before Genesis height 620538; split does not offer it`). When the other coins cover the split, it spends those and prints `Not spent: <txid>.<vout> <sats> sats: <reason>` (`notSpent` under `--json`); when they do not, it refuses with the gate's own refusal, `INSUFFICIENT_FUNDS`, the coin listed under `held` with that reason, the message ending "split records its outputs through internalizeAction after it posts them, and internalizeAction refuses a payment spending a coin mined before Genesis as not judged, so split does not spend such a coin; nothing was signed or posted. A plain `send` of the coin is not held for this reason." Nothing is signed and nothing is posted. `gift-claim` asks the BEEF it is about to post the same rule alone, and refuses by name before the post: `gift-claim refused, nothing posted: the claim spends the gift's deposit <txid>, which its proof places at height <h>, before Genesis height 620538, and internalizeAction refuses a payment spending a coin mined before Genesis as not judged, so the wallet could not record the claim.`; nothing posted, no tracker row. The hold, the check and the door judge by the same chain, the wallet's own; this release builds every wallet, a `--testnet` one too, on the toolbox's default chain, mainnet, so a `--testnet` wallet's coin is held only when it was mined below mainnet's Genesis height, 620,538, the height its door judges by. `send`, `drain`, `gift-send` and the served `/createAction` hold nothing for this reason: they post and record nothing through `internalizeAction`.
- **The received-coin rule:** 0.18.8 already passes `underReceivedRule` where the gate admits a received coin by its own reading of a checked proof at depth; the toolbox's note on 0.13.5's rule asks nothing more of this host.
- **Not reached on this host:** the toolbox's rows for a wallet on a storage client (this CLI's wallet is a local `StorageSqlx`) and for a store's door called with no wallet (this CLI's doors call `internalizeAction` through its `Wallet`, which passes its own `Chain`; `split`'s hold and `gift-claim`'s check read that `Chain` from the wallet, never from `--testnet`).
- **Tests:** `src/genesis/tests.rs` (`each_chain_names_the_genesis_height_the_door_judges_by`, `the_door_refuses_a_coin_proven_one_below_genesis_and_takes_one_at_it` through the toolbox's door, and the BEEF check's `an_unproven_spend_of_a_coin_proven_below_genesis_is_named_and_one_at_it_is_not`, `the_height_is_the_chain_asked`, `an_unproven_parent_and_a_proven_spend_name_nothing`, `an_unproven_ancestor_spending_a_coin_proven_below_genesis_is_named`); `src/commands/split.rs` (`a_split_of_a_coin_mined_before_genesis_is_refused_by_name_with_nothing_posted`, `a_split_spends_the_coin_at_genesis_and_leaves_the_one_below`, `a_send_of_the_coin_mined_before_genesis_is_not_held`, `a_split_of_the_unmined_change_of_a_send_of_such_a_coin_is_refused_by_name`); `src/commands/gift_chain.rs` (`the_claims_beef_is_asked_the_genesis_rule_alone`, `a_claim_of_a_deposit_mined_before_genesis_is_refused_before_the_post`); `tests/served_internalize_scripts.rs` (six, the served door). ## [0.18.7] - 2026-11-17

A security patch: `bsv-rs` `=0.8.11` to `=0.8.12`. `bsv-wallet-toolbox-rs` `=0.13.4` and `bsv-tracker` `=0.8.0` are unchanged (the toolbox asks `0.8.11` and the tracker `^0.8.0` of `bsv-rs`; both take 0.8.12). `Cargo.toml` moves the `bsv-rs` requirement and this crate's version; `Cargo.lock` moves two rows, `bsv-rs`'s (0.8.11 to 0.8.12, version and checksum) and this crate's own (0.18.6 to 0.18.7); no row is added or leaves; `mcp/Cargo.toml` is unchanged. No CLI code moves. Upgrade by installing 0.18.7: `cargo install bsv-wallet-cli --version 0.18.7 --locked`; `cargo install --locked` of 0.18.6 always builds `bsv-rs` 0.8.11.

- **GHSA-33fm-jcm5-4m3m** (high), patched in `bsv-rs` 0.8.12, in its summary's words cut: "the #749 link bound (GHSA-gvmh-f5gf-5vjj) meters a BEEF's serialized wire bytes but not the heap each cloned stub re-materializes, so an untrusted BEEF within the lookup resolver's size bound can force a memory-exhaustion denial of service; the fix keeps that wire budget and adds a second, heap budget beside it" (`BeefLinkLimits::max_link_heap_bytes`, default 56 MiB; a link is refused with `Error::BeefResourceLimit` when either bound is crossed). This CLI was affected through `POST /discoverByIdentityKey` and `POST /discoverByAttributes` (and the MCP `discover_by_identity_key` and `discover_by_attributes` tools, which call them): each parses every overlay host's answer, and every SLAP tracker's answer naming those hosts, with the default `Transaction::from_beef` in the toolbox's lookup, which links the answer's ancestry. No other door of this CLI links a BEEF from someone else: `internalizeAction` reads the subject without linking and its BEEF with the BEEF reader, `createAction`'s input BEEF is read with the BEEF reader, the BEEFs `receive`, `fund` and `sync` carry are built from the explorers' raw transactions and proofs or read with the BEEF reader, the gift commands read raw transactions, and `bsv-tracker` reads proofs alone (by reading, in this crate and in the toolbox's 0.13.4 and the tracker's 0.8.0 sources).
- **What now refuses**: at `POST /discoverByIdentityKey` and `POST /discoverByAttributes`, an overlay answer whose shared-parent or shared-proof links would hold more than 56 MiB of heap is refused by `Transaction::from_beef` and skipped as an invalid output (a SLAP answer's as a host it names): the door still answers 200 with the certificates it read (the answers' other outputs, and at `discoverByIdentityKey` the wallet's own), as for any output that does not parse. This includes an honest single-parent plain-payment sweep above 586 outputs, which `bsv-rs` 0.8.11's default took up to 702. Read in the sources, not run: the toolbox's lookup asks fixed overlay hosts, so no test of this repository can serve it an answer. No other input `bsv-rs` 0.8.12 refuses can be met at a command or an endpoint of this CLI.
